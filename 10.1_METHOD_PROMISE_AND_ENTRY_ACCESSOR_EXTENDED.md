## 0. Главная рамка

Внешний контракт важнее внутренней удобности.

Для этих двух семей нельзя начинать с вопроса "какой wrapper у нас уже есть". Начинать нужно с
вопросов:

1. Что это за внешний Web/JS surface?
2. Где лежит descriptor?
3. Это public method или accessor result?
4. Кто является source of truth?
5. Какая часть может быть internal coordination, а какая публично наблюдаема?
6. Можно ли публиковать выбранный carrier без нарушения `descriptor/receiver/apply path`?

Ключевое разделение:

| Слой | Что означает |
|---|---|
| Public observable surface | то, что видит внешний JS: descriptor, function/getter, receiver, toString |
| Producer/source state | откуда берутся данные: browser/profile/CDP/hidden state/native API |
| Internal coordination | вычисления, кеши, сопоставления, post-check, diag |
| Downstream/result surface | возвращенный объект, accessor результата, коллекция, Promise result |

Большинство дефектов появляется, когда internal coordination начинают публиковать как public method
или public accessor без отдельного внешнего контракта.

## 1. Extended model: `promise_method`

`promise_method` - это не отдельный внешний property-kind. Это method/data-property, чье выполнение
возвращает Promise по API-контракту.

Внешне:

- descriptor flavor: data property;
- value: callable method function;
- owner: фактический prototype/owner из runtime;
- receiver: implementation-checked;
- bad receiver: native error path;
- result: Promise с API-defined fulfillment/rejection contract;
- `Function.prototype.toString`: согласован с фактическим callable kind;
- Proxy observability: не должен появляться недопустимый exotic carrier.

Внутренне:

- `kind:'promise_method'` может помогать планировщику;
- `hooksPost` или `.then(...)` могут применяться только после native call;
- post-processing не имеет права подменять receiver/brand path;
- отсутствие данных для post-processing должно быть observable через diag/skip/fail-fast, а не
  silent fallback.

## 2. Promise method implementation mental model

Минимальная правильная мыслительная форма:

```js
function methodWrapper(...args) {
  const out = Reflect.apply(orig, this, args);
  return postProcessPromiseResult(out, this, args);
}
```

Но сама форма выше не доказывает admissibility wrapper-а. Она показывает только порядок:

1. native receiver/apply path первым;
2. native operation сам делает brand check;
3. result contract берется из native/API;
4. post-processing работает только с уже полученным result;
5. любые ошибки public invocation идут по native path, а не по project throw.

Для public Web IDL operations нельзя считать корректным любой JS wrapper только потому, что он
вызывает `Reflect.apply(orig, this, args)`. Нужно отдельно доказать, что опубликованный function
object допустим как public method carrier.

## 3. Promise method corridors

### 3.1 Native source / native public method

Самый чистый corridor:

- public method остается native;
- source state задается ниже public JS API;
- consumers читают controlled source/transit state, а не перехватывают method;
- mismatch между native source и internal state диагностируется.

Подходит, когда:

- API уже имеет native producer layer;
- данные можно задать через browser profile, CDP, browser context, permissions, UA metadata,
  hardware/backend provider или другой нижний слой;
- публичный method object чувствителен к native-code probing / carrier probing.

Примерная модель:

```text
producer/browser state -> native method -> native Promise result
                    \-> hidden/transit state -> downstream consumers
```

Практический смысл: `permissions.query` не должен становиться wrapper-ом только ради того, чтобы
раздать `mediaMicGranted` downstream. Эти флаги являются consumer-state задачей, а не основанием
менять public method identity.

### 3.2 Native call with internal observation

Допустимый corridor, если public carrier доказан или method остается native:

- вызвать native method;
- наблюдать result;
- записать internal observation;
- не менять public result, если нет доказанного return-contract corridor.

Подходит для:

- диагностики;
- синхронизации hidden state;
- проверки semantic mismatch;
- staged migration, когда публикация synthetic result пока не доказана.

### 3.3 Native call with post-processing

Самый чувствительный corridor:

- native method вызывается первым;
- Promise сохраняется как Promise;
- transformation result не нарушает API-specific shape;
- rejection behavior не нормализуется в project-specific форму;
- invalid receiver path не затрагивается.

Этот corridor нельзя применять "по умолчанию". Он требует доказательств:

- public carrier admissible;
- result object shape соответствует API;
- Promise timing не создает заметной аномалии;
- fulfillment/rejection paths соответствуют API;
- downstream state не становится partial при ошибке.

### 3.4 Native passthrough / no admissible carrier

Если method wrapper недопустим, а нижнего source layer нет, честный corridor:

- не менять public method;
- оставить native passthrough;
- отключить или ограничить зависящую cosmetic/internal логику;
- записать diag, если модуль ожидал controlled state.

Это не "провал реализации". Это корректный outcome, если альтернатива - публиковать Proxy exotic
object или ordinary JS wrapper там, где внешний контракт требует built-in function object.

## 4. Promise method anti-patterns

| Anti-pattern | Почему опасен |
|---|---|
| `core_proxy` только ради унификации | может менять public callable kind на Proxy exotic object |
| ordinary JS wrapper + `markAsNative` | native-shaped label не делает функцию built-in |
| post-process до native call | ломает receiver/brand/source ordering |
| synthetic Promise вместо native Promise | меняет timing/rejection/result provenance |
| ловить `Illegal invocation` и возвращать fallback | маскирует native bad-receiver path |
| читать `obj[key]` после patch как `orig` | orig становится wrapper-ом |
| result shape строится Core-ом без API-спеки | Core подменяет return-contract |
| public method используется как telemetry hook | telemetry меняет observable function identity |

## 5. Promise method implementation checklist

Перед публикацией или сохранением wrapper path:

1. `desc.value` действительно method/data-property?
2. `descriptorOwner` совпадает с Chromium/runtime fact?
3. `orig` захвачен из descriptor до patch?
4. Public carrier является допустимым для этой API family?
5. Если carrier - Proxy, доказано ли, что Proxy observability не нарушает внешний контракт?
6. Если carrier - ordinary wrapper, не маскируется ли он как built-in без реального основания?
7. Bad receiver идет через native method?
8. `Reflect.apply(orig, thisArg, args)` сохраняет исходный receiver?
9. Promise result остается Promise по API semantics?
10. Post-processing не меняет rejection/fulfillment shape вне API-контракта?
11. При missing producer data есть skip/fail-fast/diag, а не silent fallback?
12. Consumer-state не требует перехвата public method?

## 6. Source-native / consumer-state pattern

Это центральный pattern для чувствительных `promise_method`.

Идея:

- public method не является местом хранения controlled state;
- public method не является обязательным telemetry point;
- controlled state живет в producer/transit owner-space;
- downstream consumers читают этот state напрямую;
- public native method остается внешним oracle или native behavior.

Практическая структура:

```text
profile/input/orchestration
  -> hidden producer/transit state
  -> consumers: enumerateDevices, labels, UI/media gates, diagnostics

native browser state
  -> native public method: permissions.query / getHighEntropyValues / requestAdapter
```

Сильная сторона:

- public method kind остается чистым;
- меньше `sandboxHasNativeCode=false`;
- меньше Proxy/toString риска;
- легче диагностировать mismatch между native source и project state.

Слабая сторона:

- если native browser state и hidden transit state расходятся, это semantic mismatch;
- mismatch нельзя маскировать, его надо явно диагностировать;
- если downstream требует именно native result mutation, этот pattern может быть недостаточен.

## 7. Promise method family notes

### 7.1 `Permissions.query`

Family: public Promise-returning Web IDL operation.

Практическая рамка:

- публичный method object не должен становиться telemetry wrapper;
- permission state лучше задавать/читать как producer source;
- internal flags должны зависеть от того же source, а не от перехвата `query()`;
- если native permission не управляется, безопаснее native passthrough + diag, чем ложный wrapper.

Основной риск:

- `core_wrapper/core_proxy` или ordinary wrapper ломают function kind, даже если `toString` выглядит
  native-like.

### 7.2 `MediaDevices.enumerateDevices`

Family: public Promise-returning method с result collection.

Практическая рамка:

- method surface и device-list producer не одно и то же;
- labels/unlock state должны приходить из permission/media producer state;
- synthetic device list, если нужен, должен иметь отдельный result-contract analysis;
- public method wrapper не должен быть единственным способом синхронизировать labels.

Риск:

- direct wrapper или Proxy wrapper меняет callable kind;
- result array/object graph может дополнительно раскрыть synthetic shape.

### 7.3 `NavigatorUAData.getHighEntropyValues`

Family: promise_method внутри object-return accessor graph.

Ключевое разделение:

- `navigator.userAgentData` как accessor может быть отдельным working corridor;
- `getHighEntropyValues()` как method требует отдельной проверки callable kind и result contract.

Практическая рамка:

- HE-values лучше задавать через native UA/CH producer;
- method post-processing поверх public operation чувствителен к function kind и result provenance.

### 7.4 `GPU.requestAdapter` / `GPUAdapter.requestDevice`

Family: Promise-returning producer/factory methods.

Практическая рамка:

- method surface возвращает объект, у которого дальше есть собственный object graph;
- adapter/device Proxy на returned object - отдельный public returned-object risk;
- wrapper на method и Proxy на returned object должны оцениваться независимо.

### 7.5 `StorageManager.*`

Family: Promise-returning low-value/high-detectability methods.

Практическая рамка:

- если нет сильного producer need, native passthrough часто лучше wrapper-а;
- особенно важно не маскировать low-value spoofing ценой public callable defect.

## 8. Extended model: entry method with result accessor

Эта family состоит из пары:

1. public method entrypoint;
2. object/result surface, у которого есть отдельный accessor.

Классический пример:

```text
window.matchMedia(query) -> MediaQueryList
MediaQueryList.prototype.matches -> readonly accessor
```

Методологически это две разные entity:

| Entity | Kind | Роль |
|---|---|---|
| `window.matchMedia` | method/data-property | public entrypoint + possible internal coordination |
| `MediaQueryList.matches` | accessor property | public result surface |
| `mqlMatches` / internal cache | hidden/internal state | observation/expectation/diagnostics |

Главное правило:

internal synthetic knowledge не равно праву публиковать synthetic accessor value.

## 9. Entry/result boundary

Entry method может:

- принять аргументы;
- вызвать native method;
- проверить supported query family;
- записать internal observation;
- связать result object с hidden metadata;
- выполнить diag/post-check.

Entry method не должен автоматически:

- менять kind result accessor;
- делать result accessor public wrapper без отдельного accessor contract;
- считать internal cache authority для внешнего getter;
- подменять native result для неподдержанных query.

Result accessor должен оцениваться отдельно:

- descriptor owner;
- accessor shape;
- getter object kind;
- receiver/bad-receiver;
- `toString`;
- Proxy observability;
- semantic result path.

## 10. Entry method implementation corridor

Практическая последовательность:

1. Resolve descriptor owner для method.
2. Подтвердить data-property/callable shape.
3. Захватить `orig`.
4. Вызвать native method с исходным receiver/args.
5. Получить real result object.
6. Только после этого связать result с internal observation, если это допустимо.
7. Для unsupported/unknown query оставить native result без synthetic override.
8. Не публиковать accessor override без отдельного admissibility proof.

Мысленная форма:

```js
function entryWrapper(query) {
  const result = Reflect.apply(orig, this, arguments);
  observeResultIfSupported(result, query, this);
  return result;
}
```

И снова: сама форма не доказывает, что wrapper carrier допустим. Она только задает правильный
порядок producer boundary.

## 11. Result accessor corridors

### 11.1 Native public accessor + internal observation

Самый безопасный corridor для чувствительного result accessor:

- public accessor остается native;
- internal cache хранит expected value;
- diag сравнивает expected/native;
- public getter не подменяется.

Подходит, если:

- accessor wrapper дает proxy/toString/class-extends риск;
- нет доказанного admissible getter carrier;
- synthetic value нужен для диагностики, но не может быть безопасно опубликован.

### 11.2 Patched public accessor

Допустим только если отдельно доказано:

- accessor descriptor shape сохраняется;
- owner правильный;
- getter carrier admissible;
- bad receiver native;
- indirect stringification не раскрывает synthetic getter;
- value computation нормативна для данной query/result family.

Важно: такой accessor path не наследуется автоматически от успешного method entrypoint. Он
доказывается отдельно.

### 11.3 Native fallback for unsupported result classes

Для queries/result states, которые модуль не умеет доказательно вычислить:

- native method вызывается;
- native result возвращается;
- public result accessor остается native;
- internal observation может поставить `not_supported` / `not_proven`.

Это лучше, чем принудительно возвращать `false` или другой hardcoded result.

## 12. MatchMedia / MediaQueryList practical frame

`MediaQueryList`:

- returned platform object implementing interface `MediaQueryList`;
- не accessor и не method surface сам по себе;
- object layer между `window.matchMedia()` и `MediaQueryList.matches`;
- prototype owner для regular members: `MediaQueryList.prototype`.

`window.matchMedia`:

- method/data-property;
- может быть public entrypoint;
- может запускать internal query coordination;
- должен сохранять method identity, receiver path, descriptor shape.

`MediaQueryList.matches`:

- Web IDL `readonly attribute`, который в JS binding публикуется как readonly accessor;
- отдельный public result surface;
- не является "частью метода" в descriptor sense;
- не обязан публиковать synthetic expectation из `matchMediaInvoke`.

`mqlMatches` / internal query computation:

- hidden observation/cache;
- не public accessor authority;
- может использоваться для diag/post-check;
- не должен сам становиться наружным getter.

Практическая формула:

```text
matchMedia = entry + coordination
matches = result accessor contract
internal cache = observation, not publication authority
```

## 13. Supported vs unsupported query discipline

Для entry/result пары очень важно не превращать parser guess в public truth.

Supported query:

- query class распознан;
- source metrics известны;
- модель вычисления нормативна;
- result можно сравнить с native/expected;
- diag может сказать, какая family дала mismatch.

Unsupported query:

- query class неизвестен;
- source metrics неполны;
- parser не покрывает grammar;
- model не доказана;
- результат оставляется native.

Красный флаг: hardcoded "trash-query" policy, cutoff по длине, char-filter или эвристика
"нет media prefix -> false" как источник public `.matches`.

## 14. Receiver discipline for entry/result pairs

Entry method receiver и result accessor receiver - разные проверки.

Для entry method:

- `this` должен пройти native method check;
- cross-window / чужой Window может быть Web IDL-valid, но project-profile-invalid;
- если synthetic coordination разрешена только для текущего профилируемого window, это должно быть
  internal gate, а не замена native bad-receiver path.

Для result accessor:

- getter должен получать настоящий `MediaQueryList` receiver;
- invalid receiver должен идти native bad-receiver path;
- internal cache lookup не должен принимать произвольный object как valid receiver.

Практический вывод:

Можно иметь receiver, который валиден для native Web IDL, но не валиден для project synthetic
coordination. В этом случае native path остается, synthetic path skip/diag.

## 15. Diagnostics for entry/result pairs

Плохая диагностика:

```text
unexpected_false
```

Хорошая диагностика различает:

- unsupported query family;
- viewport metric missing;
- display metric missing;
- native/synthetic mismatch;
- receiver not profiled owner;
- accessor carrier not admissible;
- postcheck failed after partial group;
- result accessor left native by policy.

Для `matchMedia`-подобных surfaces diag должен отвечать не только "совпало/не совпало", но и
"какая feature family и какой source path участвовали".

## 16. Acceptance checks: promise_method

Минимальная приемка:

- descriptor owner/shape не изменились непреднамеренно;
- public method остается data-property callable;
- bad receiver native;
- valid receiver вызывает native first;
- Promise result сохраняет API shape;
- rejection path не нормализован project layer;
- `Function.prototype.toString.call(method)` не единственная проверка;
- indirect stringification/proxy observability учтены;
- source state и public method не смешаны;
- missing producer data дает observable skip/fail-fast/diag.

Browser/runtime checks, если требуется доказательство:

```js
const d = Object.getOwnPropertyDescriptor(owner, key);
typeof d.value === "function";
Function.prototype.toString.call(d.value);
d.value.call({});
```

И отдельно:

- carrier classification;
- Promise fulfillment shape;
- rejection behavior;
- cross-realm/cross-window behavior, если API может пересекать realm boundaries.

## 17. Acceptance checks: entry method + result accessor

Для entry method:

- method descriptor owner/shape;
- native bad receiver;
- native result object returned;
- unsupported cases return native path;
- synthetic coordination gated by proven source data;
- internal cache не observable as public property.

Для result accessor:

- accessor descriptor owner/shape;
- getter bad receiver native;
- getter carrier admissible or native-public-only;
- `toString` direct/indirect checks;
- public `.matches` не подменяется internal cache без proof;
- semantic result uses correct source family.

Для пары:

- entry method и accessor result имеют отдельные labels/diag;
- failure в accessor publication не ломает method entrypoint;
- failure в query computation не создает partial public state;
- internal expected result можно удалить/skip без изменения public descriptor.

## 18. Decision tree

### 18.1 Promise method

```text
Is it a Web IDL operation?
  -> yes: keep data-property method frame.

Can source be provided below public JS API?
  -> yes: prefer source-native / consumer-state.
  -> no: continue.

Is public wrapper carrier admissible for this family?
  -> no: native passthrough / skip / fail-fast + diag.
  -> yes: continue.

Does post-processing preserve Promise result contract?
  -> no: native passthrough / skip / fail-fast + diag.
  -> yes: native call first, post-process after, preserve receiver/bad-receiver.
```

### 18.2 Entry method with result accessor

```text
Is entry a method and result a separate accessor?
  -> yes: split contracts.

Can entry method run coordination without changing result accessor?
  -> yes: use native result + internal observation.

Is result accessor patch required?
  -> no: keep native public accessor.
  -> yes: prove accessor carrier separately.

Can query/result be computed normatively for this family?
  -> no: unsupported -> native path.
  -> yes: compare/publish only through admissible corridor.
```

## 19. Short implementation rules

1. `promise_method` is still method/data-property.
2. Promise result does not justify changing callable kind.
3. Public method is not a telemetry bus.
4. Native call/receiver check comes before post-processing.
5. `markAsNative` is not proof of built-in function object.
6. `core_proxy` is not automatically admissible for public Web IDL operations.
7. Source state should live in producer/transit owner-space when possible.
8. Object-return accessor success does not validate method wrapper success.
9. Entry method and result accessor are separate contracts.
10. Internal cache is observation, not public accessor authority.
11. Unsupported query/result classes return native behavior.
12. "Not proven" is a valid audit outcome.

## 20. Compact examples

### Promise method

```text
permissions.query:
  external kind: method/data-property, Promise result
  good mental model: native method remains public; permission state comes from source/producer
  dangerous path: wrapper only to update media flags

enumerateDevices:
  external kind: method/data-property, Promise result collection
  good mental model: device/permission state source feeds consumers
  dangerous path: public wrapper as synthetic device-list factory without carrier proof
```

### Entry method with result accessor

```text
window.matchMedia(query):
  external kind: method/data-property
  role: entrypoint and possible coordination trigger

MediaQueryList.matches:
  external kind: accessor property
  role: public result surface

internal mqlMatches:
  role: expected/observed state for diagnostics
  not role: automatic public getter authority
```

## 21. Final rule

For `promise_method`, protect public method identity first, then reason about Promise result.

For `entry method with result accessor`, split the pair before reasoning: the method may coordinate,
but the result accessor has its own descriptor/receiver/toString/proxy contract.

If the implementation cannot prove both the public carrier and the result semantics, the compliant
outcome is native passthrough / native-public-only / skip with diagnostics, not wrapper publication
by force.
