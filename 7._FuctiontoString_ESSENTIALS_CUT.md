## Что такое `Function.prototype.toString`

**`Function.prototype.toString` - это engine-native baseline текущего realm и индикатор согласованности function object. Внутренний bridge-state помогает Core связывать wrappers с native targets, но внешний контракт определяет, какой carrier, descriptor, receiver и source-of-truth допустимы для каждой surface-family.**

`Function.prototype.toString` - это нативный метод ECMAScript, который возвращает строковое представление функции.

Для JS-функций движок возвращает исходный source text функции. Для встроенных, bound, host/native callable-объектов движок возвращает native function string вида `function name() { [native code] }`. Для incompatible receiver метод выбрасывает нативный `TypeError`, потому что receiver должен быть function object.

В этом проекте `Function.prototype.toString` понимается как диагностический индикатор согласованности callable surface. 
Когда внешний тест вызывает:

```js
Function.prototype.toString.call(fn)
```

он проверяет не только строку. Он проверяет всю связку:

* `fn` является корректным callable function object;
* `receiver/apply path` сохраняет нативное поведение;
* bad-receiver path отдаёт нативную ошибку движка;
* descriptor лежит на правильном owner и сохраняет свой shape;
* `[[Prototype]]` функции согласован с её function kind;
* proxy/wrapper path не создаёт наблюдаемую подмену function/proxy kind;
* строка `toString` соответствует реальной природе callable-объекта, а не внутреннему label.

Ключевое правило:

**`Function.prototype.toString` проверяет не косметику строки, а согласованность function object с внешним нормативным контрактом.**

## Нормативная рамка

Для `Function.prototype.toString` обязательны следующие нормы:

* публичный метод живёт на `Function.prototype`;
* свойство `Function.prototype.toString` является method/data-property;
* descriptor owner остаётся `Function.prototype`;
* descriptor shape сохраняет фактические флаги движка;
* receiver должен быть function object;
* incompatible receiver проходит через нативный TypeError-path;
* user-defined/source-text функции возвращают свой source text;
* built-in/native/bound/host callables возвращают native function string по правилам движка;
* callable Proxy обрабатывается как callable Proxy exotic object, с сохранением proxy observability;
* внутренний label или bridge-state не является доказательством внешней корректности.

Для `Object.defineProperty` дополнительно сохраняется property flavor:

* data property остаётся data property;
* accessor property остаётся accessor property;
* `configurable/enumerable/writable/get/set/value` не меняются произвольно;
* non-configurable accessor не переводится в data property и не получает новые атрибуты.

Нормативные источники:

* MDN `Function.prototype.toString`: https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Function/toString
* ECMAScript `Function.prototype.toString`: https://tc39.es/ecma262/multipage/fundamental-objects.html#sec-function.prototype.tostring
* MDN `Object.defineProperty`: https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/defineProperty
* Web IDL receiver/brand checks: https://webidl.spec.whatwg.org/

## Текущее состояние window-реализации


**публичный `%Function.prototype.toString%` в window realm является engine-native baseline текущего realm.**


В window realm реализация находится в: [core_window.js](https://github.com/zugdurchfahrt/seed-noise-consistency/blob/borderline/assets/scripts/window/core/core_window.js)

Текущий модуль держит `%Function.prototype.toString%` как публичный engine-native baseline, а Proxy/JS-wrapper использует только во внутренних callable carriers.

Фактическая схема такая:

1. Модуль читает исходный descriptor:
   * `nativeGetOwnProp(Function.prototype, 'toString')`
   * `fpToStringDesc`
   * `currentRealmToString`

2. Модуль проверяет пригодность shared state:
   * `__isCoreToStringStateOk(state)`
   * `validateCoreToStringStateCandidate(state, sourceName)`
   * `resolveToStringBridgeTarget(candidate, bridgeMap)`

3. Shared state принимается только при совпадении с текущим realm baseline.

4. Публичный `%Function.prototype.toString%` приводится к `nativeToString`.

5. При установке сохраняются флаги исходного descriptor:
   * `writable: !!fpToStringDesc.writable`
   * `configurable: !!fpToStringDesc.configurable`
   * `enumerable: !!fpToStringDesc.enumerable`

6. После установки выполняется post-check:
   * фактический `Function.prototype.toString` должен быть тем же `nativeToString`;
   * ошибка установки репортится через `__emit('error', 'core_window:toString_install_failed', ...)`;
   * ошибка установки пробрасывается наружу как исключение.

## Иерархия и структура

### Уровень 0. Внешний нормативный контракт

Внешний контракт определяет допустимость реализации.

[Function.prototype.toString](https://tc39.es/ecma262/multipage/fundamental-objects.html#sec-function.prototype.tostring).

[Function.prototype.toString](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Function/toString).


Здесь фиксируются object/function/proxy/property kinds:

* `function object`
* `built-in function object`
* `bound function exotic object`
* `Proxy exotic object`
* `data property`
* `accessor property`
* `interface prototype object`

Именно это опреляет какой carrier допустим для surface.
Внутренние термины `Core` (`core_wrapper`, `synthetic_named`, `gateway`, `wrapLayer`) описывают реализацию, но не являются point of truth и не заменяют внешний контракт.

---

### Уровень 1. Engine truth

Engine truth - это реальный нативный `Function.prototype.toString` текущего JS-движка.

Он:

* живёт на `Function.prototype`;
* является обычным method/data-property;
* принимает function object как receiver;
* выбрасывает нативный TypeError на incompatible receiver;
* сериализует JS source text и native function string по правилам движка.

В [core_window.js](https://github.com/zugdurchfahrt/seed-noise-consistency/blob/borderline/assets/scripts/window/core/core_window.js) этот уровень представлен через:

* `fpToStringDesc`
* `existingToString`
* `currentRealmToString`
* `nativeToString`

Это baseline, который должен быть публично наблюдаемым.

---

### Уровень 2. Realm-local baseline

Realm-local baseline - это `Function.prototype.toString` именно текущего realm.

Для window realm важны:

* текущий `Function.prototype`;
* текущий descriptor owner;
* текущая цепочка `[[Prototype]]` function object;
* текущий baseline target;
* текущий bad-receiver path.

Shared state допускается только тогда, когда его bridge target совпадает с baseline target текущего realm.

Поэтому правило такое:

**shape-valid state является пригодным только после realm-validation.**

В [core_window.js](https://github.com/zugdurchfahrt/seed-noise-consistency/blob/borderline/assets/scripts/window/core/core_window.js) это делает:

* `validateCoreToStringStateCandidate(...)`
* `resolveToStringBridgeTarget(...)`
* проверка `stateBridgeTarget !== currentBridgeTarget`

Если shared state не совпадает с текущим realm baseline, он отклоняется с диагностикой `core_window:toString_state_rejected`.

---

### Уровень 3. Shared bridge state

**Shared bridge state - это внутреннее состояние Core для связи wrappers с их native targets**.

Граница этого уровня: **bridge state обслуживает внутренний wrapper/runtime path, но не формирует публичный ответ `Function.prototype.toString`.**

Назначение bridge state:

* хранить внутренний `nativeToString`;
* хранить `wrapper -> bridge target`;
* хранить служебные string labels для wrapper registration;
* помогать unwrap-логике;
* давать Core возможность проверять, что wrapper зарегистрирован целиком.

Текущие поля:

* `nativeToString`
* `overrideMap`
* `proxyTargetMap`

В [core_window.js](https://github.com/zugdurchfahrt/seed-noise-consistency/blob/borderline/assets/scripts/window/core/core_window.js) это публикуется как:

* `publishCoreToStringState()`
* `Core.__internal.coreToStringState`

---

### Уровень 4. Wrapper registration

**Wrapper registration - это точка, где Core связывает созданный wrapper с его native target**


* `__registerToStringWrapper(wrapped, nativeFn, wrappedName, wrapperName)`

Он выполняет три действия:

* вычисляет `bridgeTarget` через `__resolveWrappedBridgeTarget(...)`;
* пишет labels в `toStringOverrideMap`;
* пишет связь `wrapped -> bridgeTarget` в `toStringProxyTargetMap`.

После записи он сразу проверяет, что:

* label для `bridgeTarget` записан;
* `wrapped` указывает на нужный `bridgeTarget`;
* label для `wrapped` записан.

Если регистрация не совпала, модуль выбрасывает ошибку. Это важно для атомарности: wrapper не должен считаться применённым, если его bridge registration не собран полностью.

---

### Уровень 5. Wrapper factories

Wrapper factories - это фабрики, которые создают callable carriers для отдельных kind/path.

#### A. `__wrapNativeApply`

`__wrapNativeApply(nativeFn, name, applyImpl)` создаёт `Proxy(nativeFn, { apply(...) })`.

Его роль:

* принять реальный native function как target;
* выполнить пользовательский `applyImpl`;
* сохранить apply error observability через `__emit`;
* зарегистрировать wrapper через `__registerToStringWrapper(...)`.

Этот carrier допустим только там, где внешний контракт допускает такой function/proxy path.

#### B. `__wrapNativeCtor`

`__wrapNativeCtor(nativeFn, name, argsImpl)` создаёт callable/constructable Proxy.

Его роль:

* обрабатывать `apply`;
* обрабатывать `construct`;
* нормализовать аргументы через `argsImpl`;
* сохранить `.prototype` constructor-path;
* зарегистрировать wrapper через `__registerToStringWrapper(...)`.

Constructor path строже method path, потому что внешний тест чувствителен к:

* `class extends`;
* наличию и owner-у `.prototype`;
* construct/apply различию;
* prototype-chain mismatch.

#### C. `__wrapNativeAccessor`

`__wrapNativeAccessor(origGetOrSet, name, applyImpl)` является accessor carrier поверх реального native getter/setter.

Его роль:

* принять существующий native getter/setter;
* делегировать создание carrier в `__wrapNativeApply`;
* сохранить native bad-receiver path там, где `validThis` не проходит;
* не создавать source-text getter там, где нужен native getter carrier.

#### D. `__wrapAccessorGateway`

`__wrapAccessorGateway(key, getter, desc, validThis, options)` обслуживает object-return/materialized accessor routes, когда у descriptor есть реальный native getter.

Его роль:

* взять `desc.get` как carrier target;
* при invalid receiver вызвать native getter;
* при valid receiver вернуть проектное значение через `getter.call(thisArg)`;
* запретить synthetic accessor gateway без native getter.

#### E. `__wrapStrictAccessor`

`__wrapStrictAccessor(...)` сейчас является thin alias на:

* `__wrapStrictScalarAccessorGateway(...)`

Этот gateway обслуживает strict scalar accessor routes.

**strict accessor gateway является строгим коридором поверх существующего native getter, а не универсальной фабрикой для создания “нативного вида”.**


Его правило:

* native getter в descriptor является обязательным carrier target;
* bridge target разрешается через `__resolveWrappedBridgeTarget(...)`;
* invalid receiver проходит через native getter;
* synthetic strict accessor path без native getter считается contract violation.

---

### Уровень 6. `wrapGetter` и dispatcher

`wrapGetter(...)` - это внутренний dispatcher для getter-path внутри Core apply pipeline.

Он выбирает carrier по `wrapLayer`:

* strict scalar gateway;
* object-return gateway;
* materialized accessor gateway;
* native accessor wrapper;
* error path при недопустимом synthetic/no-native-getter сценарии.

`installCoreApplyTargets()` и `applyTargets` дальше связывают это с policy:

* `kind`
* `wrapLayer`
* `invokeClass`
* `descriptorOwner`
* `descriptorPath`
* `validThis`
* `invalidThis`
* `policy`

Этот уровень отвечает за то, чтобы конкретный surface не получил carrier, который противоречит его внешнему kind.

---

### Уровень 7. Per-surface patches

Per-surface patches - это конкретные API-группы:

* `Navigator.*`
* `WorkerNavigator.*`
* `Date.prototype.toLocale*`
* `Intl.*.resolvedOptions`
* `StorageManager.estimate`
* другие browser/API surfaces

Для этого уровня главный вопрос:

**какой carrier и какой source-of-truth допустим именно для данной surface-family.**

Примеры типологии:

* locale-related methods - `data property -> function value -> built-in function object`;
* strict scalar accessors - `accessor property -> native getter carrier -> scalar return`;
* array-return accessors - `accessor property -> native getter carrier -> array-like/browser value`;
* object-return accessors - `accessor property -> native getter carrier -> object/browser value`;
* promise methods - `data property -> function value -> promise-returning method`;
* constructors - constructor function object with construct path.

## Служебные labels и граница их допустимости

В текущем [core_window.js](https://github.com/zugdurchfahrt/seed-noise-consistency/blob/borderline/assets/scripts/window/core/core_window.js) отдельный публичный provider/label layer для `Function.prototype.toString` не является внешним источником истины.

Служебные labels существуют внутри:

* `toStringOverrideMap`
* `__registerToStringWrapper(...)`
* `Core.__internal.coreToStringState.overrideMap`

Их назначение:

* сопровождать bridge registration;
* помогать внутренней совместимости wrapper-path;
* проверять, что wrapper зарегистрирован вместе с target;
* давать диагностический язык Core.

Label не доказывает:

* receiver correctness;
* descriptor integrity;
* prototype owner;
* admissible carrier;
* source text vs native source;
* отсутствие proxy observability.

Поэтому правило такое:

**label описывает внутренний runtime path, а допустимость runtime path определяет внешний контракт.**

## Основная формула контракта

`Function.prototype.toString` в проекте нужно читать как систему согласованности:

1. **external normative contract**
2. **engine-native baseline**
3. **realm-local baseline**
4. **descriptor owner and descriptor shape**
5. **receiver/apply integrity**
6. **native bad-receiver path**
7. **shared bridge state validation**
8. **wrapper target mapping**
9. **proxy observability**
10. **admissible carrier для surface-family**
11. **source-of-truth parity между window / worker / runtime path**

Пока смешаны carrier и source-of-truth, дефект проявляется не как один общий `toString` crash, а как более узкий contract gap:

* bad accessor carrier;
* wrong getter shape;
* wrong function/proxy kind;
* source-text wrapper вместо native carrier;
* label-only native mask;
* window/worker source-of-truth mismatch.

## Как это соотносится с surface-группами

Глобальный системный слой `%Function.prototype.toString%` уже выровнен как engine-native baseline.

Остаточные проблемы нужно разбирать по surface-family:

* ordinary methods;
* promise methods;
* strict scalar accessors;
* array-return accessors;
* object-return accessors;
* constructor surfaces;
* async method surfaces.

Для каждой family устанавливается:

* где лежит descriptor;
* какой owner является нормативным;
* data это property или accessor property;
* какой function/proxy kind допустим;
* какой receiver path требуется;
* какой bad-receiver path является нативным;
* какой carrier допустим;
* какой source-of-truth даёт значение;
* есть ли расхождение между planner label и runtime path.

Итоговая практическая формула:
**вопрос теперь не “как сделать строку нативной”, а “допустим ли именно этот carrier/source-of-truth corridor для этой surface-family”.**

## Прикладные правила

1. Публичный `%Function.prototype.toString%` остаётся engine-native baseline текущего realm.

2. Shared bridge state допускается только после realm-validation.

3. `toStringOverrideMap` и `toStringProxyTargetMap` обслуживают внутренний bridge/runtime path.

4. Wrapper registration должна быть полной: wrapper, bridge target и labels записываются и проверяются вместе.

5. Method wrapper через Proxy/apply допустим только там, где внешний callable kind это выдерживает.

6. Constructor wrapper требует отдельной проверки apply/construct/prototype path.

7. Accessor wrapper допустим как carrier поверх реального native getter/setter.

8. Strict scalar accessor gateway требует native getter и сохраняет native invalid-receiver path.

9. Synthetic accessor/source-text path допустим только там, где он соответствует внешнему контракту surface.

10. `native-skip` является допустимым исходом, когда native surface уже соответствует контракту и патч создал бы более наблюдаемую подмену.

11. `no_admissible_carrier` является допустимым диагностическим исходом, когда текущие данные не позволяют построить carrier без нарушения внешнего контракта.

12. Любой fail/skip должен быть наблюдаемым через diag/degrade, а обязательный contract violation должен идти через throw или атомарный skip/rollback.

#### Источник `orig` (запрещены “самостоятельные поиски”)

* Модуль MUST NOT получать `orig` повторным чтением `obj[prop]` после патча.
* Hook/chain-модули MUST захватывать `orig` как `const orig = proto[method]` **до** замены.
* Standalone через `Core.applyTargets` MUST получать `orig` из `desc.value/get/set` на preflight и получать его **как параметр** в `invoke(orig, args)` (модуль не ищет оригинал сам).

#### Нормативный вызов оригинала

* `orig` MUST быть материализован как **ссылка** на `function/get/set` **до** `defineProperty`.
* `Proxy`/`Reflect`: traps обязаны соблюдать инварианты цели; нарушения (в т.ч. на `get`/prototype paths) считаются contract violation и не маскируются.
* `Object.defineProperty`: flags/shape (`configurable/enumerable/writable/get/set/value`) должны соответствовать descriptor-owner контракту, без частичных shape-drift переходов.

**Методы**

```js
return Reflect.apply(orig, thisArg, argsArray);
```

**Геттер**

```js
return Reflect.apply(origGet, thisArg, []);
```

**Сеттер**

```js
return Reflect.apply(origSet, thisArg, [value]);
```

**Promise-returning**

```js
const out = Reflect.apply(orig, thisArg, argsArray);
// дальше — только post-hooks/then, без подмены receiver/brand
return out;
```

#### WebIDL / движковый throw  Engine-throw pass-through (для публичных API)

Если вызов публичного API нарушает движковый контракт (валидность receiver/аргументов/состояния), проверка делегируется движку:
-  вызывается *нативная* реализация (getter/метод) с **тем же** `receiver` и **теми же** `args`; если движок бросает исключение — оно **пробрасывается без каких-либо изменений** (тот же тип/сообщение/объект) 
- модуль делает только **репорт факта** через `__DEGRADE__.diag(...)`.

Любые текущие THW/контрольные throw в геттерах/методах публичного API заменяются на:
канонический паттерн:

```js
try {
  return Reflect.apply(nativeFn, receiver, args);
} catch (e) {
   __loggerRoot.__DEGRADE__?.diag?.(/* ... */, e);
  throw e; // без обёрток/замены/служебных префиксов
}
```



## Что проверять при аудите

Минимальный чек-лист:

* `Function.prototype.toString` остаётся data-property на `Function.prototype`;
* значение свойства является engine-native method текущего realm;
* флаги descriptor не изменены произвольно;
* incompatible receiver выбрасывает нативный TypeError;
* shared state не принят без совпадения с realm baseline;
* wrapper не зарегистрирован без bridge target;
* `Proxy` не становится скрытой подменой там, где нужен built-in function object;
* accessor surface не превращён в data property;
* native getter/setter carrier используется только при наличии реального native getter/setter;
* source-text-created wrapper не маскируется под native, если внешний контракт требует source text;
* planner/runtime labels соответствуют фактическому runtime path;
* window/worker/provider path не расходятся по source-of-truth.

Что не доказывается статическим чтением файла:

* live browser result внешнего чекера;
* фактическое отсутствие own service keys на `window` / `self` после полного bootstrap;
* отсутствие runtime-регрессии в worker/service-worker realm;
* отсутствие residual proxy-observability gap на конкретном внешнем тесте.

Эти пункты требуют live runtime проверки в браузере или внешнем чекере.
