# Unified WRK Context
---

## 1. Исходная нормативная постановка

### 1.1. Конечные consumer scope

Система должна различать три конечных realm/scope:

1. `DedicatedWorkerGlobalScope`
2. `SharedWorkerGlobalScope`
3. `ServiceWorkerGlobalScope`

Это значит:

- конечных consumer implementation тоже три;
- конечных consumer snapshot не обязательно три по содержанию, но они три по владению и доставке;
- `Dedicated` и `Shared` могут иметь общий bootstrap-core и общий canonical producer package;
- `ServiceWorker` не должен смешиваться с этим core и требует отдельного lane.

### 1.2. Нормативная роль `scopeKind`

`scopeKind` нужен не как удобный флаг, а как hidden contract между:

- creator-side declaration,
- bootstrap-side realm validation,
- patch-side consumer logic,
- replay/delivery policy.

Допустимые значения:

- `dedicated`
- `shared`
- `service`

`type` скрипта (`classic/module`) и `scopeKind` логически не одно и то же.

### 1.3. Нормативные правила различения

Источник истины для `scopeKind` двухступенчатый:

1. creator-side declaration
   - `Worker` -> `dedicated`
   - `SharedWorker` -> `shared`
   - `serviceWorker.register()` -> `service`

2. scope-side validation
   - `self instanceof SharedWorkerGlobalScope` -> `shared`
   - `self instanceof ServiceWorkerGlobalScope` -> `service`
   - иначе при валидном worker runtime -> `dedicated`

При mismatch:

- мягкий fallback запрещён;
- `__DEGRADE__.diag` обязателен;
- normative replay для такой ветки должен прерываться.

## 2. Базовая архитектурная идея

### 2.1. Общее дерево и разделение lane

Для `Dedicated + Shared` сохраняется:

- один bootstrap core;
- одно hidden producer дерево;
- одно семейство helper-коридоров;
- одна consumer-side patch система в [WORKER_PATCH_SRC.js](C:/55555/switch/Evensteam/sunami/assets/scripts/workerscope/WORKER_PATCH_SRC.js).

Для `ServiceWorker` сохраняется отдельность:

- свой registration/import lane на window-стороне;
- свой execution/runtime lane в `ServiceWorkerGlobalScope`;
- свой read/apply path в [sw_prelude.js](C:/55555/switch/Evensteam/sunami/assets/scripts/workerscope/sw_prelude.js).

### 2.2. Почему `Dedicated` и `Shared` остаются в одном дереве

Потому что у них общий worker-family UAD/bootstrap/package слой, а расходятся они уже:

- по transport semantics,
- по replay semantics,
- по message/connect delivery,
- по final consumer delivery.

Иными словами:

- bootstrap core общий;
- helper/replay policy разная.

### 2.3. Почему `ServiceWorker` вынесен отдельно

Потому что `ServiceWorker` не просто ещё один worker consumer, а отдельная модель исполнения:

- lifecycle другой;
- event model другой;
- import/bootstrap другой;
- registration/import layer существует отдельно от runtime realm.
- существует в 

Поэтому `service` не должен пробрасываться через общий `Dedicated/Shared` коридор.

## 4. Replay и delivery semantics

### 4.1. `DedicatedWorker`

Ранние сообщения могут буферизоваться, но replay должен происходить только через event model:

- `dispatchEvent(new MessageEvent('message', ...))`

Прямой ручной вызов consumer callback не является source-of-truth.

### 4.2. `SharedWorker`

Нормативная доставка подключения должна идти через `connect` event:

- replay через `dispatchEvent(new MessageEvent('connect', { ports }))`
- не через прямой вызов `self.onconnect(...)`

Буферизовать нужно:

- не готовый handler call,
- а raw `ports[]` / connect payload.

Решение о доставке всегда принимает replay через event dispatch.

### 4.3. `ServiceWorker`

`ServiceWorker` не должен получать shared replay semantics:

- никаких `connect` replay;
- никаких shared helper-path;
- отдельный barrier и отдельный execution lane.

## 6. Hidden producer и transitional connectors

### 6.1. Что уже стало hidden-first

По текущему состоянию:

- hidden graph materialize-ится bootstrap-ом, а не добирается consumer-side кусками;
- `WORKER_PATCH_SRC` читает canonical route, а не живёт от `self.__lastSnap__` как source of truth;
- `expectedWorkerScopeKind` и `workerScopeKind` уже должны жить в hidden runtime, а не на `self`.

### 6.2. Что ещё осталось transitional residue

Несмотря на это, в механике всё ещё живы старые bridge/carrier-переходники:

- `__applyEnvSnapshot__`
- `__consumeEnvSnapshot__`
- `__installWorkerUACHMirror__`
- `__ENV_RELAY_DIAG__`
- `__GW_BOOTSTRAP__`
- nested bootstrap string внутри `WORKER_PATCH_SRC.js`

Ключевой смысл:

- transport уже существует отдельно;
- но `apply*`-слой ещё не полностью стал чистым consumer-path;
- часть локальной синхронизации всё ещё сидит на bridge-механике.

### 6.3. Почему `apply*` нельзя считать уже убранным

Потому что на нём исторически сидели и частично ещё сидят:

- `cache.snap` rebinding
- `syncWorkerEnvProfileState(...)`
- `restoreWorkerFontsState(...)`
- bootstrap replay / previous hook call
- local seed consistency

То есть `apply*` уже не чистый transport API, но ещё и не полностью удалённый residue. Это transitional combined bridge.

## 8. Inline vs transport: методологическая граница

### 8.1. Где `inline` допустим

`inline` допустим как bootstrap-carrier только там, где он:

- поднимает hidden graph заранее;
- материализует runtime root;
- передаёт canonical owner-state внутрь создаваемого worker realm;
- не создаёт новый параллельный source of truth.

Сюда относятся:

- bootstrap bundle fragments;
- inline prelude;
- inline hidden/runtime materialization;
- inline handoff для canonical owner package.

### 8.2. Где `inline` уже становится методологически неверным

`inline` неверен, если через него начинают:

- тащить произвольные куски данных как второй transport;
- подменять уже существующий `EnvBus` / `__ENV_SYNC__` path;
- создавать отдельный ad-hoc carrier только ради пары scalar values;
- разводить второй источник истины рядом с canonical worker snapshot.

Иными словами:

- inline допустим как bootstrap entry carrier;
- inline не должен становиться отдельным несвязанным data pipeline.

### 8.3. Практический вывод для текущего состояния

Для `language`, `languages`, `hardwareConcurrency`, `deviceMemory` методологически верно:

- не придумывать отдельный “маленький transport только для трёх полей”;
- использовать уже существующий canonical worker snapshot / hidden producer / consumer contour;
- inline использовать только в той степени, в какой он нужен bootstrap-у для правильного первого materialization/handoff.

## 9. Текущее состояние pipeline

### 9.1. Что уже совпало с целевой схемой

Уже собрано:

- worker-scope hidden graph materialization на bootstrap-стороне;
- canonical hidden route вместо `self.__lastSnap__` как source of truth;
- уход `scopeKind` в hidden runtime;
- выталкивание `service` из общего `Dedicated/Shared` core;
- отделение enriched envelope от исходного core snapshot;
- сужение every-sync envelope;
- переход broadcast/shared sync к consumer-path модели.

### 9.2. Что ещё не доведено до конца

Ещё не полностью снято:

- вся публичная handoff-инерция на `self`;
- полная самодостаточность hidden writer-path без transitional bridge residue;
- окончательное выравнивание initial apply, reapply и later sync в одну непротиворечивую схему;
- полное доказательство того, что все dedicated/shared consumer delivery точки уже идут только через canonical hidden producer route.

### 9.3. Что важно не перепутать

Нельзя путать:

1. hidden owner-route
2. enriched transport envelope
3. local consumer cache
4. transitional bridge
