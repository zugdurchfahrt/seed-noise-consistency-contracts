# GuardFlag / SEED contract: current pipeline lexicon

Документ фиксирует текущее нормативное состояние GuardFlag/Seed pipeline. Он не является вставочным шаблоном для массовой замены кода: текущая реализация уже находится в `assets/scripts/window/core/core_window.js`, а клиенты используют `Core.guardFlag(...)` / `Core.releaseGuardFlag(...)` из entrypoint-модулей.

При конфликте с локальной реализацией приоритет остается у внешнего нормативного контракта: descriptor shape, prototype owner, implementation-checked receiver, native bad-receiver path, observable `Function.prototype.toString`, proxy observability.

---

## 0. Связь с DEGRADE

`GuardFlagSEED` и `DEGRADE` описывают разные части одной системы:

- `GuardFlagSEED` определяет lifecycle entrypoint-модуля: token ownership, idempotency, release/lock semantics, seed owner-space.
- `DEGRADE` определяет наблюдаемость этого lifecycle: `.diag` channel, `ctx` shape, `data.outcome`, централизованную классификацию и logger buffer.
- `APPENDIX_MODULE_CODE_TEMPLATE.md` является module projection: таблицей соответствия модулей этим двум контрактам.

Правило гармонизации:

- Guard принимает решение только о владении запуском и release/lock.
- DEGRADE только наблюдает и классифицирует событие.
- Финальный `extra.type`, рассчитанный `set_log.js`, не меняет `rollbackOk`, не снимает guard и не разрешает retry.
- Любой guard exit должен быть наблюдаем через `DEGRADE` route, но отсутствие logger channel не делает patch успешным.

---

## 1. Scope

GuardFlag отвечает только за одноразовое владение запуском entrypoint-модуля в текущем realm/document.

GuardFlag не отвечает за:
- количество успешно примененных targets;
- runtime retry;
- post-check, разрешающий повторный запуск после частичного apply;
- методовые/элементные guards внутри публичных API;
- хранение Canvas/WebGL/WebGPU/Fonts state.

Допустимые итоговые состояния entrypoint:
- `return`: модуль завершился успешно, guard остается установленным;
- `skip`: preflight до write-side-effect, guard должен быть снят через `releaseGuardFlag(..., true, ...)`;
- `rollback`: fatal после apply, guard снимается только если rollback доказан как чистый;
- `throw`: fail-fast, наружу не подменяется native/engine error path там, где должен сохраняться native path.

---

## 2. Owner-state и canonical paths

Текущий owner-space:
- `window.Core` создается bootstrap layer;
- `Core.__internal` является hidden/canonical owner-space для core state;
- `Core.__internal.guards` - canonical `Map` guard-token-ов;
- `Core.__internal.__patchGuardSeq` - canonical `WeakMap` seq storage;
- `Core.__internal.prng` - canonical owner seed/PRNG state для guard token tagging и seed consumers.

Неактуально для текущего pipeline:
- `Core.__patchGuardSeq` как canonical/public storage;
- хранение guard-state в `window`;
- хранение guard lifecycle в `FernwehContext.state`;
- чтение seed для GuardFlag напрямую из `window.__GLOBAL_SEED` как owner-state.

Разрешенное чтение seed:
- bootstrap принимает public seed input (`__GLOBAL_SEED` в window realm, `CDP_GLOBAL_SEED` в worker/service-worker realm);
- `prng_seed.js` переносит seed/runtime в `Core.__internal.prng`;
- GuardFlag читает `Core.__internal.prng.seed` и `Core.__internal.prng.strToSeed`.

Если `Core.__internal.prng` отсутствует, текущая политика - fail-fast через diag + throw на уровне `core_window`.

## 3. Core API

Единственные публичные методы для клиентов:
- `Core.guardFlag(flagKey, codePrefix)`;
- `Core.releaseGuardFlag(flagKey, token, rollbackOk, codePrefix)`.

Текущая семантика `guardFlag`:
- `flagKey` приводится к строке;
- пустой `flagKey` возвращает `null`;
- если guard уже установлен, emits `<tag>:already_patched` и возвращает `null`;
- при ошибке чтения registry emits `<tag>:guard_exception` и возвращает `null`;
- при ошибке записи registry emits `<tag>:guard_write_failed` и возвращает `null`;
- при успехе возвращает token вида `ok:<guardSeedTag>:<seq>`.

Текущая семантика `releaseGuardFlag`:
- пустой `flagKey` возвращает `false`;
- `rollbackOk !== true` emits `<tag>:guard_release_skipped` и возвращает `false`;
- release разрешен только владельцу token: `Core.__internal.guards.get(flagKey) === token`;
- при успешном delete emits `<tag>:guard_released` и возвращает `true`;
- при delete/post-check failure emits `<tag>:guard_release_failed` и возвращает `false`;
- при exception emits `<tag>:guard_release_exception` и возвращает `false`.

Нормализация diag key:
- для `flagKey`, соответствующих `^__PATCH_[A-Z0-9_]+__$`, текущий `core_window` пишет diag `key: 'guard'`;
- для остальных keys используется сам `flagKey`.

---

## 4. Token / seed tagging

`guardSeedTag()` использует:
- cached `Core.__internal.prng.__guardSeedTag`, если уже есть;
- иначе `Core.__internal.prng.seed`;
- `Core.__internal.prng.strToSeed('ok|' + normalizedSeed)`, если provider доступен;
- local FNV-like hash fallback только если `strToSeed` упал или недоступен.

Fallback hash не становится новым source of truth для seed. Он только формирует диагностический token tag, чтобы guard мог остаться deterministic/idempotent внутри realm.

Важно:
- token является владением конкретным запуском;
- token нельзя подделывать или переиспользовать;
- seq хранится в `Core.__internal.__patchGuardSeq` по ключу `window`;
- fallback local counter допускается только при failure WeakMap storage и обязан быть наблюдаемым через diag.

## 5. Client entrypoint contract

Модуль-клиент обязан:
- брать guard один раз в начале entrypoint, до write-side-effects;
- использовать существующие `__flagKey`, `__tag` / module name, `__surface` или локальный diag adapter;
- при отсутствии `Core.guardFlag` emit diag `guard_missing` с `reason: 'missing_dep_core_guard'` и `outcome: 'skip'`;
- при exception из `guardFlag` emit diag `guard_failed` и `return`;
- при `!token` делать `return`, потому что `already_patched` уже эмитит Core;
- на preflight skip до apply вызвать `releaseGuardFlag(..., true, ...)`;
- на fatal после apply выполнить module-specific rollback, затем вызвать `releaseGuardFlag(..., rollbackOk, ...)`;
- после fatal не проглатывать ошибку, если по контракту требуется fail-fast.

Клиент не должен:
- копировать реализацию guard;
- создавать свой registry guard-token-ов;
- хранить guard lifecycle в `FernwehContext`;
- использовать guard на уровне отдельных методов/targets вместо entrypoint;
- снимать guard после успешного apply;
- разрешать retry после partial apply без доказанного rollback.

## 6. Observed Exit Contract

Все выходы должны быть наблюдаемы через `FernwehContext.__logger.__DEGRADE__.diag` или локальный adapter, который маршрутизирует `.diag -> callable fallback -> safe-noop`.

Shape и централизованная классификация принадлежат `3._DEGRADE_Contract.md`; Guard-контракт фиксирует только guard-specific semantics этих событий.

Текущая лексика событий:
- `already_patched` -> `outcome: 'skip'`, `reason: 'already_patched'`;
- `guard_missing` -> `outcome: 'skip'`, `reason: 'missing_dep_core_guard'`;
- `guard_failed` -> `outcome: 'skip'`, `reason: 'guard_failed'`;
- `guard_exception` -> `outcome: 'skip'`, `reason: 'guard_exception'`;
- `guard_write_failed` -> `outcome: 'skip'`, `reason: 'guard_write_failed'`;
- `guard_release_skipped` -> `outcome: 'skip'`, `reason: 'rollback_failed'`, `rollbackOk: false`;
- `guard_release_failed` -> `outcome: 'skip'`, `reason: 'guard_release_failed'`;
- `guard_release_exception` -> `outcome: 'skip'`, `reason: 'guard_release_exception'`;
- `guard_released` -> `outcome: 'rollback'`, `reason: 'rollback_ok'`, `rollbackOk: true`;
- seed missing in `rng_set` -> `outcome: 'return'`, `reason: 'bootstrap_seed_missing'`, `guard: 'locked'`.

`set_log.js` сейчас классифицирует guard errors в наблюдательные категории вроде `guard_failed`, `guard_exit`, `rollback_failed`. Это logger classification, а не lifecycle command.

## 7. Seed pipeline state

Current flow:
1. Python generates `global_seed`.
2. `main.py` injects `__GLOBAL_SEED` into window initialization.
3. Worker/service-worker seed path uses `CDP_GLOBAL_SEED`.
4. `bootstrap_hide.js` creates `Core.__internal.prng`.
5. `prng_seed.js` resolves bootstrap seed and installs:
   - `Core.__internal.prng.seed`;
   - `Core.__internal.prng.strToSeed`;
   - `Core.__internal.prng.mulberry32`;
   - `Core.__internal.prng.rand`;
   - `Core.__internal.prng.pools`.
6. Downstream graphics/media/navigator modules consume `Core.__internal.prng` as the only pipeline owner-space.

Special seed policy:
- if bootstrap seed is missing in `rng_set`, текущий код emits `rng_set:preflight:global_seed_missing`;
- guard intentionally remains locked (`guard: 'locked'`) to prevent late seed replacement;
- this is a documented policy exception and must not be silently converted into release/retry.

---

## 8. Atomicity / rollback

`rollbackOk === true` means:
- all changed descriptors/properties are restored or removed if they did not exist;
- wrapper/proxy layers installed by the failed apply are not left active;
- rollback code itself did not throw;
- module-specific state is not left in partial-applied form.

`rollbackOk !== true` means:
- guard must remain locked;
- `releaseGuardFlag` must return `false`;
- current Core emits `guard_release_skipped`.

Soft-fail is not allowed. If target behavior cannot be achieved and native path cannot be preserved, the module must report explicit diag and fail-fast where required by the normative contract.

---

## 9. Audit notes: current inconsistencies / not proven

Observed current inconsistencies that the contract must account for:
- older modules do not all use identical local helper names (`releaseEntryGuard`, `__releaseEntryGuard`, direct `Core.releaseGuardFlag` calls);
- some modules use `key: 'entry_guard'`, while current Core normalizes `__PATCH_*` keys to `key: 'guard'`;
- some post-apply failures pass `false` directly to `releaseGuardFlag`, which is correct for keeping guard locked but should remain visibly diagnosed;
- `prng_seed.js` contains emit-adapter catch blocks that intentionally swallow emit failures; this is best-effort logging behavior, not proof that all silent-swallow sites are eliminated;
- worker/service-worker paths have their own bootstrap lexicon and are not fully proven equivalent to window GuardFlag lifecycle in this audit.

Not proven in this document:
- runtime browser behavior against an external detector;
- absence of every `catch {}` in non-target modules;
- complete rollback correctness for every module;
- descriptor/native receiver invariants outside the GuardFlag/Seed scope.

## 10. Do-not-change boundaries

Do not move guard state into `window`.

Do not move guard state into `FernwehContext.state`.

Do not add states like:
- `applyStarted`;
- `partial_applied`;
- `targetsApplied`;
- `postCheckRetryAllowed`;
- `runtimeEvaluateRetry`.

Do not release guard after successful apply.

Do not replace canonical seed owner-space with ad hoc globals.

Do not edit generated/snapshot files such as `page_bundle.js` for this contract.
