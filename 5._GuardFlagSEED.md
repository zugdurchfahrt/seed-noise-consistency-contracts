# GuardFlag: (Core / Client / Инструкция)

Ниже — **3 готовых блока**: **(A) Core**, **(B) клиент для модулей**, **(C) инструкция**.  
Один раз вставляешь Core-блок, клиентский типовой блок тиражируется в entrypoint модулей.

---

## ⚠️ ВАЖНО (PIPELINE IDEOLOGY / НЕ ЛОМАТЬ ШАБЛОН)

**ЭТОТ GUARD СДЕЛАН ПОД АТОМАРНЫЙ PIPELINE.**

- Guard — про **одноразовое исполнение entrypoint модуля** (да/нет), а не про “сколько targets применилось”.
- Допустимы только цельные исходы: `return` (успех, guard остаётся) / `skip` (preflight, release) / `rollback` (fatal, release только если `rollbackOk===true`) / `throw` (fail-fast).
- **НЕ ДОБАВЛЯТЬ** В ГАРДА дополнительные состояния/эвристики (“applyStarted”, “0 targets applied”, “частично применилось”, “runtime evaluate/пост‑проверки для разрешения повторного запуска” и т.п.).
- Если есть сомнение — смотри правила **R3/R4** ниже: success = **guard не снимается**, повтор разрешён только при **доказанном rollback**.

## A) CORE-блок (материнский)

**Назначение:** единственная реализация `Core.guardFlag / Core.releaseGuardFlag`, без размазывания по модулям.

1) owner-state живёт в `Core.__internal`:
   - `Core.__internal.guards` — canonical storage guard-token-ов,
   - `Core.__internal.prng` — canonical owner seed/PRNG,
   - `Core.__patchGuardSeq` — persisted seq storage.  
2) нет silent-swallow: при исключениях — один `__emit('warn', ...)` (best-effort).
3) `window` не используется как storage для `Core.guardFlag/releaseGuardFlag`; `flagKey` остаётся внешним идентификатором, но не owner-state.

> Вставь этот блок в `core_window.js` **вместо текущих** `__patchGuardSeq/nextGuardToken/guardFlag/releaseGuardFlag` **и** перенеси `safeDefine(Core,'guardFlag'...)` и `safeDefine(Core,'releaseGuardFlag'...)` (экспорт в Core).

## B) CLIENT-блок (тиражируемый) — вставлять в entrypoint каждого модуля

**Политика:** guard управляет только *запуском модуля целиком* (entrypoint). Никаких гардов “на методы/элементы”.


```js


// ===== MODULE: canonical guard client (paste at top of entrypoint) =====
const __core = window.Core;
const __flagKey = '__PATCH_<MODULE>__';
const __tag = '<module>';
const __surface = '<surface>';

try {
  if (!__core || typeof __core.guardFlag !== 'function') {

      stage: 'guard',
      message: 'Core.guardFlag missing',
```

**Требования к интеграции:**
- Guard берётся один раз, строго в начале entrypoint, до любых write-сайд-эффектов.
- Любой ранний `return` *до apply* обязан отпустить guard через `releaseGuardFlag(..., true, ...)`.
- Любая ошибка *после apply* должна попытаться сделать rollback; `rollbackOk = !rollbackErr` (строго бинарно).
- Все exit-события (`skip/throw/rollback/return`) должны быть наблюдаемыми через `__DEGRADE__.diag` (Observed Exit Contract).

## C) Инструкция-методология  “GuardFlag: быстрое внедрение”

### C1. Границы ответственности
- **Core (`core_window.js`)**: единственная реализация `guardFlag/releaseGuardFlag`, экспорт в `window.Core`.
- **Module**: использует `Core.guardFlag(...)` и **не содержит** своей реализации guard.

### C2. Ключи
На каждый модуль:
- `flagKey`: `__PATCH_<MODULE>__` (строка; внешний идентификатор guard-а).
- canonical owner-state:
  - `Core.__internal.guards`
  - `Core.__patchGuardSeq`
  - seed/PRNG read через `Core.__internal.prng`, с допустимым transitional fallback на текущий global path, пока миграция consumers не закрыта.

### C3. Обязательные правила
**R1) Guard берём до любых write-сайд-эффектов**  
Сразу в начале entrypoint — до `defineProperty`, Proxy-обёрток, register’ов и т.п.  
Read-only проверки допустимы (наличие `window.Core`, наличие `Core.guardFlag`).

**R2) Token = владение запуском**  
`token` нельзя подделывать/переиспользовать. Release разрешён только владельцу (проверка `Core.__internal.guards.get(flagKey)===token`).

**R3) На успехе guard не снимается**  
Успешный apply = больше не запускаться в этом document.

**R4) Release только по бинарному признаку (`rollbackOk`)**  
- `rollbackOk === true` → `releaseGuardFlag(...)` разрешён.  
- `rollbackOk !== true` → `releaseGuardFlag(...)` не снимает гард (повтор запрещён).

### C4. Что такое “чистый rollback” (`rollbackOk`)
`rollbackOk=true` означает:
- все изменения дескрипторов/свойств восстановлены (или удалены, если свойства не было);
- не осталось установленных слоёв wrappers/proxy;
- rollback сам не упал.

### C5. Повторный запуск
Guard сам не делает “ретраи”. Повтор (если нужен) делает внешний оркестратор/пайплайн повторным вызовом entrypoint.
Разрешение на повтор появляется только если предыдущий запуск снял гард через `releaseGuardFlag(..., true, ...)`.

### C5.1 Namespace-контракт
- `Core.guardFlag/releaseGuardFlag` владеют только core-state внутри `Core.__internal`; guard-storage не уходит в `window` и не смешивается с `CanvasPatchContext.state`.
- `CanvasPatchContext` не является owner-space для guard lifecycle.
- `Core.__internal.prng` — canonical owner seed/PRNG для guard token tagging; `window`-globals допустимы только как transitional compatibility read, а не как owner-state.

### C6. Наблюдаемость и `throw`
`throw` в entrypoint допустим как fail-fast (чтобы видеть сбои).  
Но не допускай “служебных throw” из обёрнутых публичных API — там должен сохраняться native-путь (diag + native поведение).

### C7. Чеклист внедрения (2 минуты на модуль)
1) Вставить **B) CLIENT-блок** в начало entrypoint.  
2) Заполнить `__flagKey / __tag / __surface`.  
3) На всех preflight-выходах до write-сайд-эффектов: `diag` + `releaseGuardFlag(..., true, ...)` + `return`.  
4) В `catch`: выполнить rollback best-effort; `rollbackOk = !rollbackErr` (строго бинарно); вызвать `releaseGuardFlag(..., rollbackOk, ...)`; затем `throw`.  
5) Не копировать реализацию guard в модуль — только использовать `window.Core.*`.
