## 1. Короткая формула

`method` и `promise_method` снаружи являются не "обертками", не "core routes" и не пользовательскими custom-функциями". Внешне это Web IDL regular operations:

- свойство является data property;
- owner обычно interface prototype object, если конкретный Chromium-runtime не показывает иначе;
- `descriptor.value` является function object;
- для Web IDL public operations целевой внешний класс - built-in function object;
- вызов проходит через implementation-checked receiver;
- invalid receiver дает движковый native bad-receiver path, обычно TypeError / Illegal invocation;
- `Function.prototype.toString` и Proxy-наблюдаемость должны быть согласованы с реальным callable kind;
- return-contract берется из API-спеки, а не из Core.

`promise_method` - это проектная подкатегория `method`, а не отдельный внешний JS/Web IDL kind.
Она означает только: operation возвращает Promise или Promise-like результат по API-контракту, а
pipeline может иметь post-processing после native call. Наружный property-kind от этого не меняется.

## 2. Иерархия сущностей

Внешний слой:

| Уровень | Что проверяется |
|---|---|
| Property kind | `data property` или `accessor property` |
| Owner | где реально лежит descriptor: prototype, own, proto-chain resolved owner |
| Callable kind | built-in function object, ordinary function object, bound function exotic object, Proxy exotic object |
| Receiver path | кто является `this`, как проходит implementation check |
| Apply path | чем вызывается исходный operation: native `[[Call]]`, `Reflect.apply`, wrapper, Proxy trap |
| Result contract | конкретный API result: value, object, Promise, callback side effect |
| Observability | descriptor shape, `toString`, `ownKeys`, prototype, `class extends`, proxy behavior |

Проектный слой:

| Проектный термин | Правильное понимание |
|---|---|
| `kind:'method'` | внутренний label для regular operation / method surface |
| `kind:'promise_method'` | внутренний label для method, чей результат регулируется Promise-контрактом |
| `wrapLayer` | выбранный внутренний способ публикации или вызова |
| `wrapperClass` | описание фактического carrier path, а не доказательство корректности |
| `markAsNative` / native-shaped | маска/совместимость для `toString`, не доказательство built-in kind |
| `core_wrapper` / `core_proxy` | возможный internal carrier, но не внешний норматив сам по себе |

Главное: internal label не меняет внешний kind. Если label говорит "method", а runtime публикует
Proxy exotic object или ordinary JS wrapper там, где внешне ожидается built-in method object, это
расхождение label/runtime/contract.

## 3. Method как property surface

Обычный method surface в Web IDL - это не accessor. Он не имеет getter/setter descriptor. Внешняя
форма:

```js
const desc = Object.getOwnPropertyDescriptor(owner, key);
// ожидаемый flavor:
// {
//   value: function key(...) { [native code] },
//   writable: true,
//   enumerable: usually true for Web IDL operations,
//   configurable: true
// }
```

Практическое правило:

- method проверяется через `desc.value`;
- accessor проверяется через `desc.get` / `desc.set`;
- нельзя переносить логику method в accessor corridor и наоборот;
- нельзя считать `navigator.userAgentData` и `navigator.userAgentData.getHighEntropyValues()` одним
  и тем же kind: первое - object-return accessor, второе - promise-returning method.

Типичные method / promise_method surfaces из локального inventory:

| Family | Примеры |
|---|---|
| Permissions / media / storage | `Permissions.query`, `MediaDevices.enumerateDevices`, `StorageManager.estimate`, `persist`, `persisted` |
| UA-CH | `NavigatorUAData.getHighEntropyValues`, `NavigatorUAData.toJSON` |
| WebGPU | `GPU.requestAdapter`, `GPUAdapter.requestDevice`, `GPUAdapter.requestAdapterInfo` |
| Screen/media-query | `window.matchMedia`, `screen.toJSON`, `visualViewport.toJSON` |
| Canvas/WebGL | `HTMLCanvasElement.getContext`, `toBlob`, `toDataURL`, 2D/WebGL prototype methods |
| Audio/fonts/RTC | `BaseAudioContext.createBuffer`, `FontFaceSet.load`, `RTCPeerConnection.createOffer` |
| Locale/Intl | `Date.prototype.toLocale*`, `Intl.*.prototype.resolvedOptions` |

## 4. `promise_method`: что меняется и что не меняется

`promise_method` меняет только result discipline, но не property kind.

Не меняется:

- data-property form;
- descriptor owner;
- callable value;
- receiver/brand check;
- native bad-receiver path;
- `Function.prototype.toString` expectations;
- Proxy observability expectations.

Меняется:

- native call returns a Promise or API-defined Promise result;
- post-processing, если он вообще допустим, должен идти после native call;
- rejection/throw path должен сохранять API semantics;
- отсутствие данных для post-processing не должно превращаться в silent fallback.

Нормативная apply-форма для Promise-returning method:

```js
const out = Reflect.apply(orig, thisArg, argsArray);
// дальше допустим только contract-safe post-processing результата,
// без замены receiver, без подмены brand-check, без userland bad-receiver classification.
return out;
```

Если API-спека говорит `Promise<PermissionStatus>`, `Promise<MediaDeviceInfo[]>`,
`Promise<GPUAdapter | null>` или другой конкретный тип, этот result contract задает API-спека.
Core не имеет права "выдумывать" return shape.

## 5. Receiver и apply path

Для method surfaces `this` - не косметика. Это часть Web IDL invocation contract.

Контрольная модель:

1. Берется исходный `orig` до публикации replacement descriptor.
2. При вызове используется тот же receiver, который дал пользовательский call.
3. Native operation сам выполняет implementation check.
4. Если receiver неверный, наружу проходит native engine error.

Корректная мыслительная схема:

```js
function wrapper(...args) {
  return Reflect.apply(orig, this, args);
}
```

Что ломает contract:

- вызывать `orig(args)` без сохранения `this`;
- жестко подставлять `window`, `navigator`, `screen` или другой "удобный" receiver;
- ловить native TypeError и заменять его на project error;
- классифицировать bad receiver по тексту сообщения;
- сначала менять result, а потом пытаться имитировать native receiver path;
- повторно читать `obj[key]` после patch, принимая wrapper за orig.

Detached call - важная проверка:

```js
const f = navigator.permissions.query;
f.call({ name: "not-permissions" }, { name: "camera" });
```

Методологически нас интересует не конкретная строка ошибки, а то, что ошибка пришла из native
implementation-check path и не была подменена проектной логикой.

## 6. Descriptor owner и prototype owner

Method surface должен жить там, где его реально публикует Chromium/Web IDL binding. Чаще всего это
interface prototype object, но для некоторых Web/Window surfaces owner может быть runtime-dependent.

Нельзя угадывать owner по названию API. Нужно разделять:

- нормативное ожидание Web IDL;
- фактический Chromium shape;
- project route.

Проверки:

```js
let owner = null;
let obj = target;
while (obj) {
  const desc = Object.getOwnPropertyDescriptor(obj, key);
  if (desc) {
    owner = obj;
    break;
  }
  obj = Object.getPrototypeOf(obj);
}
```

Для method:

- `desc` должен быть data descriptor;
- `value` должен быть callable;
- flags должны совпадать с runtime fact;
- `defineProperty` применяется к реальному owner, а не к удобному объекту;
- создание own shadow-property поверх prototype method без внешнего основания является shape drift.

Для `window.matchMedia` локальные материалы специально фиксируют: owner может быть resolved runtime
owner, а не заранее навязанный `Window.prototype`.

## 7. Function.prototype.toString как система согласованности

`Function.prototype.toString` проверяет не только текст. Он проявляет согласованность:

- callable kind;
- realm baseline;
- function prototype chain;
- native/built-in vs ordinary source;
- Proxy/callable exotic path;
- bridge/label state;
- receiver behavior при вызове самого `toString`.

Важное разделение:

| Слой | Что значит |
|---|---|
| Engine truth | реальный `%Function.prototype.toString%` текущего realm |
| Realm baseline | текущий `Function.prototype`, текущая function topology |
| Bridge state | внутренние maps для wrapper -> target, только служебная связность |
| Label layer | строковая маска, совместимость и диагностика |
| Public function object | фактический объект, который видит внешний тест |

`markAsNative` может сделать ordinary JS wrapper "native-shaped" в простом `toString.call(fn)`, но
не превращает его в built-in function object. `Proxy(nativeFn,{ apply })` может быть callable и
native-shaped, но все равно остается Proxy exotic object.

Поэтому вопрос не "показывает ли строка `[native code]`". Правильный вопрос:

- допустим ли этот carrier для данной family;
- не раскрывается ли source wrapper в косвенных путях (`String(fn)`, `'' + fn`, `class extends fn`);
- не возникает ли recursion/prototype/proxy anomaly;
- согласованы ли label, bridge target и фактический object kind.

## 8. Proxy observability и carrier admissibility

Proxy - нормативная ECMAScript сущность, но это не автоматически корректный public carrier для Web
IDL operation.

Разница:

- Proxy может иметь `[[Call]]`, если target callable.
- Но Proxy остается exotic object.
- Web IDL regular operation снаружи ожидается как built-in function object.
- Если внешний анализатор различает built-in function object и Proxy exotic callable, маска
  `function x() { [native code] }` не закрывает defect.

Отсюда правило:

`core_proxy` допустим только там, где он реально сохраняет внешний contract и снижает проблему
receiver/brand/descriptor. Его нельзя выбирать только ради унификации или потому что "так удобнее".

Типовые proxy-риск симптомы:

- failed proxy observability;
- failed object toString;
- too much recursion;
- reflect set prototype failure;
- class extends раскрывает wrapper source;
- descriptor shape выглядит правильно, но callable kind не совпадает.

## 9. Взаимодействие method surfaces с accessor surfaces

Большая часть путаницы возникает на границе "accessor возвращает объект, у объекта есть методы".

Примерная карта:

| Surface | Внешний kind | Что важно |
|---|---|---|
| `Navigator.userAgentData` | object-return accessor | public surface - getter/accessor |
| `NavigatorUAData.getHighEntropyValues()` | promise_method | public surface - method/data-property на returned object prototype |
| `navigator.mediaDevices` | object-return/accessor path | public access to object graph |
| `MediaDevices.enumerateDevices()` | promise_method | separate method surface |
| `window.matchMedia()` | method | entrypoint, может запускать internal coordination |
| `MediaQueryList.matches` | accessor | published result surface, не method |

Нельзя переносить претензию к method carrier на уже рабочий accessor carrier без доказательства.
Также нельзя прикрывать method defect тем, что "похожий объект-return accessor работает".

Правильная фраза:

object-return accessor и public prototype method - разные entity families. Они могут быть связаны
одним downstream graph, но их descriptor/receiver/apply path проверяется отдельно.

Для media-query pair это нужно фиксировать буквально:

- `window.matchMedia()` — public method/data-property entrypoint;
- возвращаемый `MediaQueryList` — platform object, implementing interface `MediaQueryList`;
- `MediaQueryList.prototype` — interface prototype object;
- `MediaQueryList.matches` — не method, а Web IDL `readonly attribute`, который в JS binding
  публикуется как accessor property на `MediaQueryList.prototype`.

## 10. Method как producer boundary

Некоторые methods являются factory/producer entrypoints:

- `HTMLCanvasElement.getContext`
- `OffscreenCanvas.getContext`
- `window.matchMedia`
- `GPU.requestAdapter`
- `navigator.permissions.query`
- `navigator.mediaDevices.enumerateDevices`

У таких методов есть двойная роль:

1. public method surface с внешним descriptor/receiver/toString contract;
2. вход в downstream graph, где появляются контексты, result objects, internal state или caches.

Ошибка возникает, когда downstream-state начинают публиковать через сам public method wrapper. Метод
может запускать coordination, но его public callable identity не должна становиться контейнером для
служебной логики.

Безопасная модель:

- public method сохраняет native-compatible method surface;
- native call происходит первым или receiver-check делегируется native;
- downstream state живет в hidden owner/transit state;
- result post-processing не ломает return-contract;
- если public method не имеет admissible carrier, правильным итогом может быть native passthrough
  плюс internal observation/diag, а не wrapper любой ценой.

## 11. Interaction matrix

| Пересечение | Правильная постановка вопроса | Типовой риск |
|---|---|---|
| Method + descriptor | Это data descriptor на фактическом owner? | accessor/data drift, own shadow |
| Method + receiver | Native operation получает исходный `this`? | Illegal invocation из-за потерянного receiver |
| Method + apply | `orig` захвачен до patch и вызван через `Reflect.apply`? | повторное чтение wrapper как orig |
| Method + toString | public callable kind согласован с native-shaped view? | ordinary wrapper с label-mask |
| Method + Proxy | Proxy действительно admissible для этой family? | Proxy exotic object вместо built-in |
| Promise method + result | Promise/result type взят из API-спеки? | Core синтезирует чужой return shape |
| Method + accessor graph | entrypoint и result accessor разделены? | internal cache публикуется как accessor authority |
| Method + worker/window | source-of-truth совпадает между realm-ами? | window/worker semantic mismatch |
| Method + diagnostics | ошибка наблюдаема без служебного throw наружу? | silent-swallow или project throw в public API |

## 12. Typology quick reference

### 12.1 Ordinary method

Признаки:

- data property;
- callable `value`;
- возвращает синхронный результат, объект, primitive или выполняет side effect/callback;
- receiver/brand может быть строгим;
- post-processing допустим только если не ломает native receiver/apply path и return-contract.

Примеры:

- `window.matchMedia`
- `PluginArray.item`
- `CanvasRenderingContext2D.getImageData`
- `WebGLRenderingContext.getParameter`
- `Date.prototype.toLocaleString`
- `Intl.DateTimeFormat.prototype.resolvedOptions`

### 12.2 Promise method

Признаки:

- все признаки ordinary method;
- result является Promise по API-контракту;
- errors/rejections должны соответствовать API semantics;
- post-processing идет после native call и не заменяет receiver/brand path.

Примеры:

- `Permissions.query`
- `MediaDevices.enumerateDevices`
- `StorageManager.estimate`
- `NavigatorUAData.getHighEntropyValues`
- `GPU.requestAdapter`
- `GPUAdapter.requestDevice`
- `FontFaceSet.load`

### 12.3 Factory method

Это method, но с producer-boundary ролью. Он выдает объект, на котором дальше живет отдельный graph.

Примеры:

- `HTMLCanvasElement.getContext`
- `OffscreenCanvas.getContext`
- `AudioContext.createAnalyser`

Для factory method особенно важно не смешивать public callable identity и issued-instance patching.

### 12.4 Entry method with result accessor

Пример:

- `window.matchMedia()` выдает `MediaQueryList`;
- `MediaQueryList.matches` является accessor result surface.

Метод может участвовать в internal coordination, но accessor result surface остается отдельным
контрактом. Internal expectation/cache не равен праву публиковать synthetic `.matches`.

## 13. Что считается доказанным и недоказанным

Доказано, если есть:

- внешний нормативный basis;
- фактический Chromium/runtime descriptor owner/shape;
- проверенный receiver/bad-receiver path;
- проверенный callable kind или доказанный carrier path;
- проверенный `toString` в прямом и косвенном путях;
- согласованность planner label / runtime path / diagnostic label.

Не доказано, если:

- есть только internal label `kind:'method'`;
- есть только native-looking строка `function x() { [native code] }`;
- нет проверки фактического owner;
- нет проверки bad receiver;
- неизвестно, ordinary wrapper это или Proxy exotic carrier;
- result совпал в одном сценарии, но не проверен return-contract family;
- browser/runtime не проверялся, а вывод сделан по коду.

В методичке допускается пометка "не доказано". Это лучше, чем превращать догадку в правило.

## 14. Минимальный audit checklist для method/promise_method

1. Surface является method или на самом деле accessor?
2. Где фактический descriptor owner?
3. Descriptor является data descriptor?
4. `value` callable?
5. Фактический callable kind: built-in, ordinary JS function, Proxy exotic, bound function?
6. Какой receiver ожидает native API?
7. Что происходит при bad receiver?
8. `orig` захватывается до patch?
9. Native call идет через `Reflect.apply(orig, thisArg, argsArray)` или эквивалентный engine call?
10. Если это `promise_method`, кто задает Promise result contract?
11. Есть ли post-processing, и не меняет ли он receiver/brand/return-contract?
12. `Function.prototype.toString.call(fn)` согласован?
13. Проверены ли indirect stringification paths?
14. Есть ли Proxy observability defect?
15. Согласованы ли internal labels с фактическим runtime path?
16. При невозможности patch есть atomic skip/rollback/pass-through и `.diag`?

## 15. Практические красные флаги

- `method` публикуется как accessor или accessor как method.
- `promise_method` трактуется как отдельный внешний property kind.
- `markAsNative` используется как доказательство built-in function object.
- `Proxy(nativeFn, { apply })` считается "нативным" только по строке `toString`.
- Bad receiver ловится и заменяется на project-specific throw.
- `orig` читается после patch.
- Data descriptor превращается в accessor descriptor.
- Prototype method shadowed own-property без runtime basis.
- Internal cache/result state публикуется как public accessor value без отдельного accessor contract.
- `css media passed` или похожий функциональный smoke-result считается достаточным для descriptor/receiver/toString acceptance.
- Silent catch вокруг apply/post-process скрывает contract violation.

## 16. Сводное правило

Для `method` / `promise_method` правильность определяется не тем, что wrapper "работает", и не тем,
что `toString` показывает `[native code]`.

Правильность определяется тем, что весь внешний path остается согласованным:

- property kind: data property;
- owner: фактический prototype/owner из runtime;
- value: function object нужного внешнего класса;
- receiver: native implementation check;
- apply: native call через сохраненный receiver/args;
- bad receiver: native engine path;
- result: API-specific return contract;
- toString: realm baseline + callable kind + bridge/label consistency;
- Proxy: нет недопустимой exotic observability;
- diagnostics: ошибки apply/preflight/post-check наблюдаемы, но служебка не летит наружу.

Если хотя бы один из этих пунктов не доказан, surface не считается contract-clean. Если пункт
доказан как нарушенный, это не "косметика toString", а contract defect соответствующего слоя.
