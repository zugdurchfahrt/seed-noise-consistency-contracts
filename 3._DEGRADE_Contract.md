# DEGRADE contract: единая диагностика, наблюдаемые выходы и интеграция с Guard

Документ фиксирует нормативную роль `__DEGRADE__.diag` в текущем pipeline и его связь с GuardFlag/Seed-контрактом.

Главное разделение ответственности:
- `DEGRADE` владеет диагностическим каналом, формой `ctx`, централизованной сериализацией и классификацией наблюдаемых событий;
- `GuardFlagSEED` владеет lifecycle entrypoint-модуля, idempotency, семантикой rollback/release и seed owner-space;
- `3.1_DEGRADE_APPENDIX_MODULE_CODE_TEMPLATE.md` является проекцией модулей: таблицей соответствия модулей общей модели, но не переопределяет нормы этого документа и `5._GuardFlagSEED.md`.

При конфликте с внешним нормативным контрактом приоритет остается у `ECMAScript spec`, `Web IDL Standard`, наблюдаемого поведения MDN/Chromium: descriptor shape, prototype owner, implementation-checked receiver, native bad-receiver path, observable `Function.prototype.toString`, proxy observability.

## 2. Основные термины

`diag channel`:
`FernwehContext.__logger.__DEGRADE__.diag(level, code, ctx, err)`.

`base callable fallback`:
`FernwehContext.__logger.__DEGRADE__(code, err, extra)`.

`safe-noop`:
Если нет ни `.diag`, ни callable fallback, adapter возвращает управление без `console.*` и без throw. Это разрешено только для сбоя logging-path; это не делает сам patch успешным.

`Observed Exit`:
Любой контролируемый path `return`, `skip`, `rollback` или `throw`, который эмитится до выхода из контролируемого шага.

`Native path`:
Для public API hooks модуль обязан сохранять native receiver/apply behavior. Служебная диагностика не должна заменять native `TypeError`, `Illegal invocation`, promise rejection или результат движка.

## 3. Единые роли: DEGRADE vs Guard

`DEGRADE` - это слой наблюдения:
- принимает structured events;
- сериализует небезопасные host/DOM/cyclic data;
- нормализует `level`, `code`, `key`, `scope`, `scopeKind` и final `extra.type`;
- классифицирует guard/preflight/apply/rollback/native events для представлений логгера;
- хранит entries только в private logger/degrade state.

`GuardFlagSEED` - это слой lifecycle:
- получает token владения entrypoint-модуля через `Core.guardFlag(flagKey, codePrefix)`;
- сохраняет idempotency успешных apply, не снимая guard;
- снимает guard только на pre-apply skip или clean rollback;
- оставляет guard locked при partial/failed rollback;
- использует `Core.__internal.prng` для deterministic token tagging.

Ни один контракт не должен переопределять другой:
- Guard lifecycle events должны эмититься через `DEGRADE` route.
- `DEGRADE` classification не означает, что guard можно release.
- `ctx.type` не должен переписывать module `policy`.
- `policy` не должен подавлять обязательную observed diagnostics.

## 5. API `.diag`

Нормативный вызов:

```js
FernwehContext.__logger.__DEGRADE__.diag(level, code, ctx, err);
```

Текущая реализация в `set_log.js`:
- допустимые `level`: `info | warn | error | fatal`; invalid level становится `info`;
- `code` приводится к строке, default `unknown`;
- non-plain `ctx` становится `{}`;
- `ctx.data === null` сохраняется;
- отсутствующий `ctx.data` становится `{}`;
- non-object/non-function `ctx.data` становится `{}`;
- data сериализуется централизованно с лимитами для host/cycle/string;
- explicit `ctx.key: null` сохраняется;
- omitted `ctx.key` синтезируется из `ctx.diagTag`, затем из `ctx.module`;
- final `extra.type` формируется централизованной `normalizeDiagType(...)`;
- `.diag` fail-safe и не должен throw в module code.

Важно: модули передают raw `ctx.type`; logger может классифицировать final `extra.type` в значения вроде `guard_failed`, `guard_exit`, `preflight_failed`, `apply_failed`, `rollback_failed`, `native_throw`, `pipeline diagnostic` или `browser diagnostic`. Эта классификация нужна только для наблюдения и фильтрации. Она не меняет `policy`, не снимает guard и не разрешает retry.

## 6. Обязательный `ctx` shape

События модулей должны передавать:

```js
{
  module,
  diagTag,
  surface,
  key,
  stage,
  message,
  type,
  data
}
```

Обязательные соглашения:
- `module`: stable module id.
- `diagTag`: stable event producer tag; default - module id.
- `surface`: stable owner-route/lane label, не обязательно имя файла.
- `key`: string или `null`; опускать только когда намеренно используется central key synthesis.
- `stage`: одно из допустимых значений ниже.
- `message`: stable human-readable message.
- `type`: input cause category, не policy.
- `data`: object или `null`; для controlled exits включать `data.outcome`.

Допустимые `ctx.stage`:

`bootstrap | preflight | guard | apply | rollback | contract | hook | runtime | cleanup | audit`

Принадлежность stage:
- `bootstrap`: bootstrap owner-transfer / bootstrap cleanup.
- `guard`: guard acquisition, guard absence, already-patched exits или guard-read/write failure до module apply.
- `preflight`: read-only capability/data checks до write side effects.
- `apply`: descriptor/property/wrapper installation и post-apply checks.
- `rollback`: descriptor/state restoration и guard release после pre-apply skip или rollback.
- `contract`: normative invariant checks.
- `hook`: runtime hook chain diagnostics.
- `runtime`: runtime/native pass-through diagnostics.
- `cleanup`: logger/bootstrap cleanup paths.
- `audit`: synthetic logger/probe audit events.

Не вводить локальные stage strings.

## 7. `type` и Missing Data

Для missing-data causes использовать строго:
- `pipeline missing data`: наши profile/seed/meta/bridge/internal expected data отсутствуют или inconsistent;
- `browser structure missing data`: engine/browser structure отсутствует, изменилась, non-configurable, receiver/brand incompatible или native path неожиданно throws.

Другие stable input types, которые сейчас используются pipeline:
- `ok`
- `contract violation`
- `pipeline telemetry`
- module-specific stable cause labels

Logger может нормализовать final `extra.type` для фильтрации. Missing-data input strings всё равно важны: они позволяют central classification в `pipeline diagnostic` / `browser diagnostic`, когда не срабатывает более строгий event classifier.

## 8. `data.outcome`

Controlled exits должны включать:

`data.outcome` in:

`return | skip | rollback | throw`

Значение:
- `return`: controlled success/native/no-op return.
- `skip`: controlled non-apply или non-retry path.
- `rollback`: clean rollback завершен или rollback path является intended observed path.
- `throw`: fail-fast или native/engine throw path намеренно сохраняется.

Рекомендуемые stable `data.reason` values для shared filtering:
- `already_patched`
- `missing_dep_core_guard`
- `guard_failed`
- `guard_exception`
- `guard_write_failed`
- `guard_release_failed`
- `guard_release_exception`
- `rollback_failed`
- `rollback_ok`
- `preflight_failed`
- `apply_failed`
- `native_throw`
- `bootstrap_seed_missing`

## 9. Guard events через DEGRADE

Guard acquisition events:
- `guard_missing`: `stage: 'guard'`, `outcome: 'skip'`, `reason: 'missing_dep_core_guard'`
- `guard_failed`: `stage: 'guard'`, `outcome: 'skip'`, `reason: 'guard_failed'`
- `already_patched`: `stage: 'guard'`, `outcome: 'skip'`, `reason: 'already_patched'`

Core release events:
- `guard_release_skipped`: `stage: 'rollback'`, `outcome: 'skip'`, `reason: 'rollback_failed'`, `rollbackOk: false`
- `guard_release_failed`: `stage: 'rollback'`, `outcome: 'skip'`, `reason: 'guard_release_failed'`
- `guard_release_exception`: `stage: 'rollback'`, `outcome: 'skip'`, `reason: 'guard_release_exception'`
- `guard_released`: `stage: 'rollback'`, `outcome: 'rollback'`, `reason: 'rollback_ok'`, `rollbackOk: true`

Текущая logger classification:
- guard failures схлопываются в final `extra.type: 'guard_failed'`;
- `already_patched` схлопывается в final `extra.type: 'guard_exit'`;
- `guard_release_skipped` с `reason: 'rollback_failed'` классифицируется как `rollback_failed`.

Это expected behavior. Final logger classification не является lifecycle decision.

## 10. Минимальный module flow

Допустимая последовательность:

1. Bootstrap/read-only resolution ссылок logger/Core.
2. Guard acquisition до write side effects.
3. Read-only preflight под guard.
4. Apply descriptor/property/wrapper changes.
5. Post-apply contract checks.
6. Success `return` с guard kept locked.

Pre-apply skip:

1. Эмитить observed skip.
2. Вызвать `releaseGuardFlag(..., true, ...)`.
3. Return.

Post-apply fatal:

1. Эмитить apply failure в соответствии с ситуацией.
2. Откатить descriptor/state changes.
3. Вызвать `releaseGuardFlag(..., rollbackOk, ...)`.
4. Throw или preserve native path as required.

Не читать это как `releaseGuardFlag(true)` после success. Successful apply означает, что guard остается установленным для document/realm.

## 11. Приоритет policy

`policy` принадлежит target/group planning, а не `ctx.type`.

Правила:
- `policy: 'throw'` или `policy: 'strict'` означает fail-fast для patch step.
- `policy: 'skip'` может skip target/group только если native behavior остается intact и skip observed.
- `rollback` обязателен после partial apply, когда module owns restoration.
- Public API hooks должны сохранять native receiver/apply path; service errors не должны leak вместо native engine behavior.
- Если `throw` приведет к leak service internals из public API hook, использовать native pass-through/engine throw path и эмитить diagnostics out-of-band.

## 12. Module-local Adapter

Назначение: маршрут `.diag -> callable fallback -> safe-noop` без `Illegal invocation`, без `console.*` и без local policy decisions.

Нормативные свойства adapter:
- привязывает `.diag` через `__D.diag.bind(__D)`;
- не throws;
- не вызывает `console.*`;
- не мутирует caller-provided `extra`;
- может shape module defaults (`module`, `diagTag`, `surface`, `key`) перед вызовом `.diag`;
- не делает local classification `ctx.type` и не invents `ctx.stage`.

Canonical pattern:

```js
const __loggerRoot = (C && C.__logger && typeof C.__logger === 'object') ? C.__logger : null;
const __D = (__loggerRoot && typeof __loggerRoot.__DEGRADE__ === 'function') ? __loggerRoot.__DEGRADE__ : null;
const __diag = (__D && typeof __D.diag === 'function') ? __D.diag.bind(__D) : null;

function __emit(level, code, ctx, err) {
  try {
    const safeErr = (typeof err === 'undefined') ? null : err;
    if (__diag) return __diag(level, code, ctx || null, safeErr);
    if (typeof __D === 'function') {
      const safeCtx = (ctx && typeof ctx === 'object') ? ctx : {};
      const safeLevel = (level == null) ? 'info' : level;
      return __D(code, safeErr, Object.assign({}, safeCtx, { level: safeLevel }));
    }
  } catch (emitErr) {
    return undefined;
  }
  return undefined;
}
```

Bootstrap-исключение:
`bootstrap_hide.js` может исполняться до logger installation. Его adapter может safe-noop до появления `FernwehContext.__logger.__DEGRADE__`. Это не разрешает alternative logging channel.

## 13. Constraints

Запрещено:
- `console.*` как единственный diagnostic path;
- новые stage strings вне allowed set;
- local reclassification, которая disagree с `set_log.js`;
- treating `ctx.type` as policy;
- releasing guard после successful apply;
- retry после partial apply без clean rollback;
- storing guard state в `window` или `FernwehContext.state`;
- describing export surfaces как owner-state;
- hiding service failures by returning non-native public API values.

- runtime success against external detectors;
- отсутствие каждого silent-swallow во всех modules;
