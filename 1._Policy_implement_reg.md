
# Единая политика реализации: `object/function/proxy/property/apply path` contract

## 0. Назначение документа

- Контроль СООТВЕТСТВИЯ internal path  entities ВНЕШНЕМУ нормативному contract;
- устранение  расхождений между planner/runtime/label layer;
- установлнние консистентности используемых внутренних ярлыков.

Документ фиксирует единую политику соблюдения нормативных внешних требований, способов реализации архитктуры модулей.

## 1. Нормативный внешний слой инвариантов

Нормативная иерархия такая:

- **Object**
  - бывает **ordinary object** или **exotic object**. ECMAScript прямо различает их по набору внутренних методов. [ECMA-262](https://tc39.es/ecma262/multipage/ecmascript-data-types-and-values.html#sec-object-type)
- Если объект вызываемый, у него есть `[[Call]]`, и это уже **function object**. [ECMA-262](https://tc39.es/ecma262/multipage/fundamental-objects.html#sec-function-instances)

- Среди function/object-форм есть нормативные виды:
  - **built-in function object**
  - **bound function exotic object**
  - **Proxy exotic object**  
  Источники: [ECMA-262 object type](https://tc39.es/ecma262/multipage/ecmascript-data-types-and-values.html#sec-object-type), [ECMA-262 proxy objects](https://tc39.es/ecma262/multipage/ordinary-and-exotic-objects-behaviours.html#sec-proxy-objects)


Ещё один слой различения идет не по “классу объекта”, а по **виду свойства**:
- **data property**: у свойства есть `value`
- **accessor property**: у свойства есть `get`/`set`

А для Web IDL surface это обычно так:
- **regular attribute** -> accessor property на **interface prototype object**
- **regular operation / method** -> data property, чьё значение это **built-in function object**, с implementation-checked `this`  
Источники: [Web IDL attributes](https://webidl.spec.whatwg.org/#es-attributes), [Web IDL operations](https://webidl.spec.whatwg.org/#es-operations)

Поэтому возможны исключительно следующие НОРМАТИВЫНЕ сущности:
- `Object`
- `ordinary object`
- `exotic object`
- `function object`
- `built-in function object`
- `bound function exotic object`
- `Proxy exotic object`
- `data property`
- `accessor property`
- `interface prototype object`.


- `Proxy`/`descriptor`/`toString`-инварианты берутся из ECMAScript, а не из `Core`:
  [ECMAScript spec](https://tc39.es/ecma262/),
  [Global object](https://tc39.es/ecma262/#sec-global-object),
  [Property Attributes](https://tc39.es/ecma262/#sec-property-attributes),
  [Property Descriptor Specification](https://tc39.es/ecma262/#sec-property-descriptor-specification-type),
  [Function.prototype.toString](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Function/toString),
  [Object.defineProperty](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/defineProperty).
- `Illegal invocation`
  [Object Internal Methods and Internal Slots](https://tc39.es/ecma262/#sec-object-internal-methods-and-internal-slots)
 
  [Web IDL Standard](https://webidl.spec.whatwg.org/).
  /brand/“объект действительно реализует интерфейс” **берутся из Web IDL, а НЕ из `Core`**:
  Здесь источник для `platform object`:
  [platform objects](https://webidl.spec.whatwg.org/#js-legacy-platform-objects)
  `implements interface`:
   [Platform objects implementing interfaces](https://webidl.spec.whatwg.org/#is-a-platform-object),
  `implementation-check`:
  [Interfaces](https://webidl.spec.whatwg.org/#js-interfaces)
  getter/method invocation.
- return-contract конкретного API берётся уже из API-спеки, а **НЕ из `Core`**:
  Permissions / MediaDevices / Storage / WebGPU / Web Audio / HTML и т.д.
  То есть `Promise<PermissionStatus>`, `MediaDeviceInfo[]`, `GPUAdapter | null` и иные формы возврата  **`Core` НЕ устанавливает по собственному разумению**.

 См. [внешние источники и нормативы поведения](#external-sources).

  ### `Function.prototype.toString` 

  * живёт на `Function.prototype`
  * является обычным method/data-property
  * ожидает корректный receiver
  * знает, как сериализовать:

    * native/built-in functions
    * user-defined functions
    * bound functions
    * callable proxies/host callables по правилам движка

  Это **эталон**.
  Не  label, не override, не Proxy, а именно движковый baseline.

 `Function.prototype.toString` — это **realm-specific baseline**, то есть не просто “какая-то функция toString”, а:

  * именно текущий realm
  * именно текущий `Function.prototype`
  * именно текущая цепочка function object prototype


  `Function.prototype.toString.call(fn)` проверяет не только текст:

  * что это вообще **callable function object**
  * что у него не сломан receiver-path
  * что он не попал в рекурсию через bridge
  * что его prototype/bridge/Proxy-layer не собраны криво
  * согласованность между:
    * самой функцией,
    * её `[[Prototype]]`,
    * тем, что возвращает `toString`,
    * и тем, как она ведёт себя при чужом `this`


  `Function.prototype.toString` — это **не одна функция**, а **система согласованности** между:

  * исходной нативной функцией,
  * текущим realm baseline,
  * shared toString state,
  * wrapper/proxy target chain,
  * label map,
  * prototype chain,
  * конкретными patched functions.

## 3. Проектный слой - ПРИНЦИПЫ:

Проектный слой ОБЯЗАН следовать главным правилам:

- сохранение internal path соответсвующим внешнему нормативному contract.
-  установлнние консистентности используемых внутренних ярлыков: Внутренний label определяет только  описание реализации.
- устранение  расхождений между planner/runtime/label layer: Если label и runtime расходятся, исправляется внутренний язык.


Проектный слой ОБЯЗАН сохранять нормативный `descriptor/receiver/apply path`:

- `descriptor shape`
- `prototype owner`
- `implementation-checked receiver`
- `native bad-receiver path`
- observable `Function.prototype.toString`
- proxy observability

## Mandaratory Chelicks Question-list

### 1. Object / Function / Proxy / Property Kinds

Для каждого целевого surface установить в соответствии с нормативным внешним слоем инвариантов:

- что это снаружи:
  `data property`, `accessor property`, `method`, `promise_method`, constructor, namespace member и т.д.;
- какой это object/function kind по фактическому runtime-path:
  ordinary object, function object, built-in function object, Proxy exotic object и т.д.;
- не подменён ли исходный kind внутренним wrapper path так, что это меняет observable contract.

### 2. Descriptor / Receiver / Apply Path

Для каждого целевого surface установить согласно нормативному внешнему слоемю инвариантов:

- где реально лежит descriptor;
- совпадает ли `descriptorOwner` с Chromium/runtime fact;
- сохраняется ли expected `configurable/enumerable/writable/get/set/value` shape;
- сохраняется ли корректный `receiver` path;
- сохраняется ли native bad-receiver throw path;
- идёт ли вызов по прямому native path или через wrapper/proxy/gateway path;
- не ломает ли path `Reflect.apply`, `brand check`, `Illegal invocation`, `instanceof`, `prototype` или `toString`.

### 3. Internal Labels Consistency

Проверить, согласованы ли между собой:

- planner labels
- registry/diag labels
- runtime path
- фактический object/function/proxy kind

Если label и runtime расходятся, это фиксируется как отдельный defect:

- label не должен подменять внешний контракт;
- label не должен описывать “замысел”, если runtime строит другой механизм;
- внутренне верное значение = то, которое честно описывает фактический runtime path.

Если runtime ломает:

- `descriptor shape`
- `prototype owner`
- `receiver/apply path`
- `Function.prototype.toString`
- `proxy observability`

то дефект признается контрактным.

## Required Scope

Для pipeline установитьь:

- producer / source of data
- bootstrap / routing / ownership
- planner / preflight
- executor / apply path
- public observable surface
- diagnostics / degrade / rollback path
-  меру зависимости модуля от hidden namespace / bootstrap owner / worker scope / service worker scope.

---

## Контрольные критерии


1. Какой фактический runtime path реализован.
2. Совпадают ли с  внешней нормативной рамкой установленнык:
   - object/function/proxy/property kinds,
   - descriptor shape,
   - receiver/apply path,
   - planner/runtime labels.
3. Убедиться в отутствии расхождений по:
   - producer / routing / ownership,
   - planner,
   - executor,
   - diagnostics,
   - public API contract layer.

---

## Constraints

- Не подменять содержание внешего норматива внутренними терминами произвольного содержания, не соответвтующими внешней нормативной рамке по типу: `wrapperClass`, `core_wrapper`, `synthetic_named`, `gateway` и т.д.
- Не считать internal label доказательством correctness сам по себе.
- Не делать вывод “path правильный”, если это доказано только planner label-ом.
- Не делать вывод “path неправильный”, если не проверен внешний contract.
- Не смешивать:
  - Python orchestration state,
  - JS bootstrap state,
  - hidden owner-state,
  - public runtime surface.

---

## Final Rule

Внешний contract определяет допустимость реализации.

Внутренний label определяет только честное описание реализации.

`window` не запрещается как нормативный public/runtime target realm.

Запрет касается только использования `window` как:
- canonical owner-state,
- internal compatibility transit,
- service-function transit,
- operational residue после owner-transfer.

Если label и runtime расходятся, исправляется внутренний язык.
