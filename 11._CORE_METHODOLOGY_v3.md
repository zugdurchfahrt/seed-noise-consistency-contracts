# Core Apply Methodology

## 0. Назначение, статус и приоритет

Документ описывает нормативный порядок использования [core_window.js](https://github.com/zugdurchfahrt/seed-noise-consistency/blob/borderline/assets/scripts/window/core/core_window.js)
(`Core`) как bootstrap-owner, toString bridge, structural preflight/planner, wrapper-provider, guard-provider
и registry-provider.

---



Этот документ является прикладным контрактом для `Core`. Он не заменяет внешние нормы `ECMAScript`,
`Web IDL`, `Chromium/MDN`.

Приоритет при конфликте:

1. Внешний нормативный контракт [ECMAScript spec](https://tc39.es/ecma262/)/ [Web IDL Standard](https://webidl.spec.whatwg.org/) / MDN / Chromium-runtime fact.
2. Единая политика реализации `object/function/proxy/property/apply path`: [Policy implement register](./1._Policy_implement_reg.md).
3. Function shape: [Function.toString Essentials](./7._FuctiontoString_ESSENTIALS_CUT.md).
4. Этот документ как прикладная методология использования [core_window.js](https://github.com/zugdurchfahrt/seed-noise-consistency/blob/borderline/assets/scripts/window/core/core_window.js).

Ключевое правило:

**`Core`не придумывает внешний контракт API**. `Core` **обеспечивает**, чтобы выбранный module/context path
не нарушал `descriptor`/`receiver`/`apply`/`toString`/`proxy` invariants внешнего контракта**

---

## 1. Scope

Документ распространяется на window-realm Core:

[core_window.js](https://github.com/zugdurchfahrt/seed-noise-consistency/blob/borderline/assets/scripts/window/core/core_window.js)

Документ описывает:

- как понимать первую часть файла Core: bootstrap, logger adapter, `safeDefine`, toString baseline,
  wrapper factories;
- как понимать вторую часть файла Core: `Core.preflightTarget`, `Core.applyTargets`, `Patch Group`,
  guard, registry, apply/rollback plan;
- как module/context должны вызывать Core;
- какие поля target-контракта обязательны;
- в каком порядке выполняются preflight, planning, apply, registry, rollback;
- какие части Core являются публичным contract API, а какие внутренней инфраструктурой;
- как Core связан с DEGRADE, GuardFlag/SEED, Function.prototype.toString и method-surface контрактами.

Документ не разрешает:

- добавлять новые `kind` в Core;
- вводить локальные wrapper/toString/nativizer механики в модулях;
- переносить доменную логику профиля/seed/rules в Core;
- применять synthetic fallback вместо native bad-receiver path;
- обходить Core preflight при patching public Web/API descriptors;
- использовать устаревшие target-данные из `__outdated_CORE2.0-vCurrent.md`.

## 2. Внешняя нормативная рамка

Core всегда обслуживает внешний контракт, а не наоборот.

Нормативные понятия берутся из:

- [ECMAScript objects/functions/proxy/property descriptors](https://tc39.es/ecma262/)
- [ECMAScript `Function.prototype.toString`](https://tc39.es/ecma262/multipage/fundamental-objects.html#sec-function.prototype.tostring)
- ECMAScript Proxy exotic objects:
  https://tc39.es/ecma262/multipage/ordinary-and-exotic-objects-behaviours.html#sec-proxy-objects
- MDN `Function.prototype.toString`:
  https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Function/toString
- MDN `Object.defineProperty`:
  https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/defineProperty
- MDN `Reflect.apply`:
  https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Reflect/apply
- Web IDL attributes and operations:
  https://webidl.spec.whatwg.org/#es-attributes
  https://webidl.spec.whatwg.org/#es-operations

Из этого следуют базовые внешние сущности:

| Слой | Нормативная сущность |
|---|---|
| Object | ordinary object / exotic object / platform object |
| Function | function object / built-in function object / bound function exotic object / Proxy exotic object |
| Property | data property / accessor property |
| Web IDL | interface prototype object / regular attribute / regular operation |
| Invocation | receiver path / implementation check / native bad-receiver path |
| Observability | descriptor shape / owner / own keys / prototype / toString / proxy behavior |

Проектные термины `kind`, `wrapLayer`, `wrapperClass`, `core_wrapper`, `named_wrapper`,
`descriptor_only`, `strict_accessor_gateway` являются внутренними labels. Они не заменяют внешний
контракт и не доказывают корректность сами по себе.

## 3. Роли и границы

### 3.1 Core

`Core` в [core_window.js](https://github.com/zugdurchfahrt/seed-noise-consistency/blob/borderline/assets/scripts/window/core/core_window.js) является bootstrap-owner и structural planner.

Core отвечает за:

- logger adapter к `FernwehContext.__logger.__DEGRADE__`;
- safe define route через `safeDefine`;
- realm-local `Function.prototype.toString` baseline;
- shared toString bridge state;
- wrapper registration;
- core wrapper factories;
- guard lifecycle;
- seed/guard owner-space через `Core.__internal`;
- target registry и dedupe;
- read-only target preflight;
- planning через `Core.applyTargets`;
- descriptor post-check в `planItem.apply`;
- rollback primitive в `planItem.rollback`.

Core не отвечает за:

- доменные profile/rules/seed values конкретного API;
- выбор данных для Canvas/WebGL/Navigator/WebGPU/Fonts;
- порядок групп разных модулей;
- browser launch, CDP orchestration, mitmproxy;
- внешнюю API-спеку результата;
- silent fallback за модуль.

### 3.2 Context

`context` является слоем применения для контекстных API, прежде всего Canvas/WebGL в Window realm.

Context отвечает за:

- порядок применения patch groups;
- hook registration;
- issued object/context patching;
- module-specific post-check;
- group rollback;
- сохранение native references там, где контекстный слой их использует;
- применение Core preflight там, где context сам делает `Object.defineProperty`.

Context не должен:

- создавать независимый toString bridge;
- обходить Core при descriptor-sensitive public surface;
- выбирать `wrapLayer` автоматически там, где контракт target требует явный corridor;
- превращать hook-domain логику в Core.

### 3.3 Module

`module` является доменным слоем.

Module отвечает за:

- surface inventory;
- profile/source-of-truth;
- seed/profile/rules/hook logic;
- построение target contracts;
- observed diagnostics;
- entrypoint guard lifecycle;
- group apply/rollback, если standalone-модуль совмещает роли `module + context`.

Module не должен:

- подменять public native API вне принятой Core-линии;
- читать `orig` после patch;
- создавать локальные nativizer/toString/Proxy registries;
- hardcode-ить profile values вместо существующих profile/window/state sources;
- проглатывать ошибки без DEGRADE diag.

## 4. Обязательные части [core_window.js](https://github.com/zugdurchfahrt/seed-noise-consistency/blob/borderline/assets/scripts/window/core/core_window.js)

Текущий Core состоит из нескольких нормативных зон. При изменении или использовании Core нельзя
рассматривать `Core.applyTargets` отдельно от первой части файла, потому что wrapper/toString/diag
инварианты поднимаются раньше.

### 4.1 Bootstrap prelude и logger adapter

Core получает `window.FernwehContext`, берет logger root и строит adapter:

- preferred path: `FernwehContext.__logger.__DEGRADE__.diag(level, code, ctx, err)`;
- fallback path: callable `__DEGRADE__(code, err, extra)`;
- logger-path failure не бросает новое исключение и не пишет в `console.*`.

Это соответствует `3._DEGRADE_Contract.md`: отсутствие logger channel не делает patch успешным, но
сам logging-path должен быть fail-safe.

### 4.2 `safeDefine`

`safeDefine(obj, prop, descriptor)` является Core-route для `Object.defineProperty`.

Норма:

- define failure диагностируется через `core_window:safeDefine:define_failed`;
- stage зависит от причины: `apply` для define failure, `guard` для missing target;
- ошибка пробрасывается, если define path критичен.

`safeDefine` не является разрешением менять descriptor shape произвольно. Он только безопасный
исполнитель уже выбранного descriptor plan.

### 4.3 Realm-local `Function.prototype.toString`

Core обязан поднять публично корректный `%Function.prototype.toString%` текущего realm.

Нормативные элементы:

- `fpToStringDesc`;
- `existingToString`;
- `currentRealmToString`;
- `nativeToString`;
- `resolveToStringBridgeTarget`;
- `validateCoreToStringStateCandidate`;
- `publishCoreToStringState`;
- `Core.__internal.coreToStringState`.

Shared state пригоден только после realm-validation. Если bridge target не совпадает с текущим realm
baseline, state отклоняется с diag `core_window:toString_state_rejected`.

### 4.4 Wrapper registration

`__registerToStringWrapper(wrapped, nativeFn, wrappedName, wrapperName)` связывает wrapper с bridge target.

Норма:

- bridge target вычисляется через `__resolveWrappedBridgeTarget`;
- label пишется для bridge target;
- wrapper пишется в `toStringProxyTargetMap`;
- label пишется для wrapper;
- сразу выполняется post-check регистрации;
- при mismatch регистрация считается failed и бросает ошибку.

Wrapper не считается примененным, если его toString bridge registration не собран полностью.

### 4.5 Core wrapper factories

Допустимые factory routes:

| Factory | Назначение |
|---|---|
| `__wrapNativeApply` | method/apply carrier поверх реальной native function |
| `__wrapNativeCtor` | callable/constructable carrier для constructor-sensitive path |
| `__wrapNativeAccessor` | accessor carrier поверх реального native getter/setter |
| `__wrapAccessorGateway` | object-return/materialized accessor route при наличии native getter |
| `__wrapStrictAccessor` | strict scalar accessor route через `__wrapStrictScalarAccessorGateway` |

Factories не являются универсальным способом "сделать нативный вид". Они допустимы только там, где
target contract разрешает соответствующий carrier.

### 4.6 Guard, registry и planner zone

Внутри `installCoreApplyTargets` Core публикует:

- `Core.applyTargets`;
- `Core.preflightTarget`;
- `Core.resolveDescriptor`;
- `Core.__targetRegistry`;
- `Core.isTargetRegistered`;
- `Core.registerPatchedTarget`;
- `Core.guardFlag`;
- `Core.releaseGuardFlag`;
- `Core.__safeDefine`;
- wrapper factories и `Core.wrapGetter`.

Эта зона связывает `3._DEGRADE_Contract.md`, `5._GuardFlagSEED.md` и target-planning pipeline.

## 5. Публичные Core API и правила вызова

### 5.1 `Core.preflightTarget(target)`

Read-only structural validation одного target.

Использовать, когда:

- context сам применяет descriptor, но обязан заранее проверить owner/kind/wrapLayer;
- нужен read-only fail-fast до side effects;
- нужно доказать `descriptorOwner` через `resolve=proto_chain`;
- нужно проверить strict accessor gateway contract до define.

Не использовать как:

- замену group planning;
- разрешение на apply без post-check;
- способ получить profile value.

### 5.2 `Core.applyTargets(targets, profile, diag)`

Batch planner.

Возвращает `planned[]`, где каждый `planItem` содержит:

- `owner`;
- `requestedOwner`;
- `key`;
- `kind`;
- `invokeClass`;
- `wrapLayer`;
- `policy`;
- `origDesc`;
- `desc`;
- `nextDesc`;
- `apply`;
- `rollback`;
- `skipApply`;
- `reason`;
- `targetId`;
- `tag`.

`Core.applyTargets` планирует и строит wrappers, но group atomicity остается обязанностью caller-layer.
Caller должен применить все plan items или откатить уже примененные.

### 5.3 `Core.resolveDescriptor(owner, key, options)`

Descriptor resolver.

Допустимые modes:

- `own`;
- `proto_chain`.

Норма:

- patch применяется на resolved `descriptorOwner`;
- исходный requested owner сохраняется только как diagnostic/context data;
- если external runtime показывает descriptor выше по prototype chain, define должен идти туда.

### 5.4 `Core.guardFlag` / `Core.releaseGuardFlag`

Entrypoint lifecycle API.

Использовать на уровне module entrypoint, до write side effects. Не использовать как per-method guard.

Семантика и observed exits регулируются `5._GuardFlagSEED.md`.

### 5.5 `Core.registerPatchedTarget`

Registry/dedupe API.

Норма:

- registry обновляется только после успешного полного group apply;
- registry не обновляется после partial apply;
- при rollback registry не должен фиксировать target как успешно примененный;
- если registry API отсутствует, это diagnostic event, а не повод молча продолжить как будто dedupe сохранен.

### 5.6 Wrapper factories как public Core API

Модули могут использовать factory API только если target contract уже доказал допустимость carrier.

Не допускается:

- использовать `__wrapNativeApply` только ради cosmetic toString;
- применять Proxy carrier для whole module без per-target основания;
- использовать `__wrapNativeCtor` для обычного method path;
- создавать accessor gateway без native getter, кроме explicitly materialized path, где это разрешено текущим Core contract.

## 6. Target contract

Каждый target должен быть self-contained contract object. Он описывает surface, а не произвольное
желание модуля переписать свойство.

Минимальная форма:

```js
{
  owner,
  key,
  kind,
  wrapLayer,
  policy,
  diagTag
}
```

Расширенная форма:

```js
{
  owner,
  key,
  kind,
  wrapLayer,
  policy,
  resolve,
  invokeClass,
  validThis,
  invalidThis,
  getImpl,
  setImpl,
  invoke,
  hooksPost,
  value,
  allowCreate,
  mode,
  targetId,
  diagTag
}
```

### 6.1 Обязательные поля

| Поле | Норма |
|---|---|
| `owner` | object/function, откуда начинается descriptor resolution |
| `key` | non-empty string |
| `kind` | `data`, `accessor`, `method`, `promise_method` |
| `wrapLayer` | явный corridor; отсутствие или `auto` не является нормативным target-contract |
| `policy` | `skip`, `throw`, `strict` |
| `diagTag` | stable producer tag |

### 6.2 Допустимые `kind`

| `kind` | Внешний смысл |
|---|---|
| `data` | data property replacement |
| `accessor` | accessor property, getter/setter descriptor |
| `method` | Web/JS operation as data property with function value |
| `promise_method` | method/data-property, результат которого должен быть Promise-like |

Новые `kind` запрещены как Core architecture branch. Если нужен post-processing результата, он должен
выражаться через `method` или `promise_method`, а не через новый target kind.

### 6.3 Допустимые `wrapLayer`

| `wrapLayer` | Норма использования |
|---|---|
| `descriptor_only` | только `kind=data` |
| `named_wrapper` | non-brand-strict method/accessor path при доказанной допустимости JS wrapper |
| `strict_accessor_gateway` | strict scalar accessor route, `kind=accessor`, `policy=strict`, обычно `resolve=proto_chain` |
| `object_return_gateway` | object-return accessor route, `kind=accessor`, `policy=strict`, `resolve=proto_chain` |
| `materialized_accessor_gateway` | materialized accessor route, `kind=accessor`, `policy=strict`, допускает owner-first materialization согласно текущему Core |
| `core_wrapper` | native apply/accessor carrier через Core Proxy factories |

`wrapLayer='auto'` не является нормативным target-contract. Если исторический код содержит auto-like
поведение, оно должно рассматриваться как compatibility legacy, а не как методология.

### 6.4 `invokeClass`

| `invokeClass` | Норма |
|---|---|
| `normal` | default method path, не требует strict receiver gate |
| `brand_strict` | Web IDL/implementation-checked receiver path, требует `validThis` и `core_wrapper` |
| `constructor` | constructor-sensitive path, требует `core_wrapper` |
| `meta_primitive` | slot/meta-sensitive path, требует `core_wrapper` |

Для `brand_strict`, `constructor`, `meta_primitive` synthetic wrapper path запрещен.

### 6.5 `resolve`

| `resolve` | Норма |
|---|---|
| `own` | проверять только `owner` |
| `proto_chain` | искать descriptor по prototype chain и применять на resolved `descriptorOwner` |

Для strict accessor gateways, которым нужен реальный owner/shape contract, `resolve=proto_chain`
является обязательным.

## 7. Preflight methodology

Preflight является read-only стадией. Он не должен создавать wrapper, менять descriptor, писать registry
или делать profile mutation.

Порядок preflight:

1. Проверить `owner`.
2. Проверить `key`.
3. Нормализовать и проверить `policy`.
4. Проверить `kind`.
5. Нормализовать и проверить `invokeClass`.
6. Нормализовать и проверить `wrapLayer`.
7. Проверить совместимость `kind/wrapLayer`.
8. Проверить совместимость `policy/wrapLayer`.
9. Проверить совместимость `invokeClass/wrapLayer`.
10. Проверить `resolve` и необходимость `proto_chain`.
11. Выполнить `resolveDescriptor`.
12. Зафиксировать `descriptorOwner`.
13. Проверить duplicate target в текущем batch.
14. Проверить duplicate target в Core registry.
15. Проверить descriptor presence или `allowCreate`.
16. Проверить descriptor flavor:
    - data shape для `kind=data`;
    - accessor shape для `kind=accessor`;
    - data function value для `kind=method/promise_method`.
17. Проверить configurable/writable.
18. Проверить known wrapped functions/getters/setters.

Preflight failure должен быть observed через DEGRADE:

- `stage: 'preflight'`;
- `data.outcome: 'skip'` или `'throw'` по policy;
- stable `reason`;
- `type: 'pipeline missing data'` или `browser structure missing data` по причине.

## 8. Apply Targets methodology

`Core.applyTargets` превращает валидный target list в Patch Group plan.

Порядок `applyTargets`:

1. Принять только array targets.
2. Если список пуст, observed empty skip/return через diag.
3. Создать batch-local `seenOwners`.
4. Для каждого target выполнить `preflightTarget`.
5. При preflight failure:
   - emit через `diagDegrade`;
   - при `throw/strict` бросить;
   - при `skip` вернуть failed planned object без partial plan.
6. Создать `planItem` на resolved `descriptorOwner`.
7. Dispatch по `kind`:
   - `patchDataProp`;
   - `patchAccessor`;
   - `patchMethod`;
   - `patchPromiseMethod`.
8. Сформировать `nextDesc`.
9. Прикрепить `planItem.apply`.
10. Прикрепить `planItem.rollback`.
11. Вернуть `planned[]`.

Важное разделение:

- Core делает structural planning и создает wrapper/descriptor plan.
- Caller-layer делает group execution.
- Registry side effects выполняются только после полного успешного group apply.

## 9. Dispatch methodology

### 9.1 `patchDataProp`

Норма:

- `kind=data` использует `descriptor_only`;
- descriptor flavor должен быть data;
- `non-configurable + non-writable` не патчится;
- `nextDesc` сохраняет исходные descriptor flags;
- новое значение берется только из target/profile/source-of-truth, а не из hardcode.

Риск:

- наличие `wrapperClass` на data path должно рассматриваться как non-normative compatibility branch,
  если оно не подтверждено отдельным внешним контрактом.

### 9.2 `patchAccessor`

Норма:

- descriptor должен иметь accessor shape;
- non-configurable accessor не патчится;
- strict accessor gateway требует `policy=strict`;
- strict/object-return gateway не принимает `setImpl`;
- native getter должен быть carrier для strict/object-return gateway;
- `set` сохраняется из исходного descriptor, если strict gateway contract требует preservation;
- invalid receiver должен идти через native path, если есть original getter/setter.

Accessor не должен превращаться в data property, если внешний контракт не разрешает shape-change.

### 9.3 `patchMethod`

Норма:

- descriptor должен быть data property;
- `desc.value` должен быть function;
- `non-configurable + non-writable` не патчится;
- `brand_strict/constructor/meta_primitive` требуют `validThis` и `core_wrapper`;
- `normal + core_wrapper` запрещен текущим Core preflight;
- native call выполняется через captured `orig`;
- `hooksPost` для обычного method не должен менять non-string результат в текущем implementation path.

### 9.4 `patchPromiseMethod`

Норма:

- внешне это обычный method/data-property;
- Core label `promise_method` означает только Promise-result discipline;
- native call выполняется первым;
- результат обязан быть promise-like;
- при non-thenable result: diag `<tag>:promise_contract_failed` + throw;
- `hooksPost` применяются только в `.then(...)`;
- hook exception не заменяет native result: diag `<tag>:hooksPost_failed`, вернуть исходный resolved result.

См. `10._METHOD_SURFACES.md` и `10.1_METHOD_PROMISE_AND_ENTRY_ACCESSOR_EXTENDED.md`.

## 10. Patch Group methodology

Patch Group - это batch of planned targets, а не новый Core kind.

Нормативная форма group execution:

```js
const plans = Core.applyTargets(targets, profile, []);
const applied = [];
try {
  for (const p of plans) {
    if (!p || p.skipApply) continue;
    p.apply();
    applied.push(p);
  }

  for (const p of applied) {
    Core.registerPatchedTarget(p.owner, p.key);
  }
} catch (e) {
  let rollbackErr = null;
  for (let i = applied.length - 1; i >= 0; i--) {
    try {
      applied[i].rollback();
    } catch (re) {
      if (!rollbackErr) rollbackErr = re;
    }
  }
  if (rollbackErr) throw rollbackErr;
  throw e;
}
```

Практическая норма:

- применять plan items последовательно;
- считать group successful только после всех post-checks;
- registry выполнять только после полного успеха;
- rollback выполнять в обратном порядке;
- rollback failure диагностировать отдельно;
- guard release разрешать только если rollback доказан как clean.

Если module/context по исторической причине делает `Object.defineProperty(p.owner, p.key, p.nextDesc)`
самостоятельно, он обязан выполнить тот же post-check, rollback и registry discipline. Предпочтительный
путь для новых правок - `p.apply()` / `p.rollback()`.

## 11. `orig` / native behavior

`orig` - это captured reference до descriptor replacement.

Источники `orig`:

- для `method/promise_method`: `desc.value`;
- для accessor getter: `desc.get`;
- для accessor setter: `desc.set`;
- для context hook path: reference, захваченная до define.

Норма вызова:

- method: `Reflect.apply(orig, thisArg, argsArray)`;
- getter: `Reflect.apply(origGet, thisArg, [])`;
- setter: `Reflect.apply(origSet, thisArg, [value])`;
- promise method: native call first, Promise post-processing later.

Запрещено:

- читать `obj[key]` после patch, чтобы заново получить original;
- заменять native bad-receiver path project error;
- возвращать fallback value вместо `Illegal invocation`, если внешний контракт требует native throw.

## 12. Function.prototype.toString methodology

Core toString bridge имеет четыре уровня.

### 12.1 Engine truth

`Function.prototype.toString` текущего движка является baseline.

Он:

- живет на `Function.prototype`;
- является method/data-property;
- принимает function object receiver;
- бросает native `TypeError` на incompatible receiver;
- сериализует source text/native function string по правилам движка.

### 12.2 Realm-local baseline

Для window realm важны:

- текущий `Function.prototype`;
- текущий descriptor owner;
- текущая `[[Prototype]]` chain function object;
- текущий baseline target;
- native bad-receiver path.

Shared state можно принять только если bridge target совпадает с текущим realm baseline.

### 12.3 Shared bridge state

Bridge state обслуживает внутренний wrapper/runtime path, но не формирует публичный ответ сам по себе.

Текущие поля:

- `nativeToString`;
- `overrideMap`;
- `proxyTargetMap`.

### 12.4 V8 Stack Trace Alignment (Proxy Exotic Object)

По спецификации ECMAScript, вызов `Function.prototype.toString` на несовместимом receiver (например, `Object.create(func).toString()`) выбрасывает `TypeError`.
Однако V8 формирует `.stack` этого исключения по-разному в зависимости от того, как была извлечена функция `toString`:
- Для нативной функции V8 пишет фрейм: `at Function.toString (<anonymous>)`.
- Если функция унаследована через `Proxy exotic object`, V8 (видя Proxy) пишет фрейм: `at Object.toString (<anonymous>)`.

Поскольку внешний контракт (MDN/ECMAScript) требует полной невидимости внутреннего механизма реализации (proxy observability = false), `Core` обязан устранять этот implementation-defined артефакт V8.
Для этого в ловушках `get` корневых фабрик (`__wrapNativeApply`, `__wrapNativeCtor`) свойство `toString` лексически изолируется во вторичный Proxy, который перехватывает нативный `TypeError` и перезаписывает `.stack`, возвращая фрейм к эталонному виду `at Function.toString`. Это восстанавливает нормативный вид, который нарушается внутренними механиками движка V8 при работе с Proxy.

Публикация:

- `publishCoreToStringState()`;
- `Core.__internal.coreToStringState`.

### 12.5 Wrapper registration

Любой wrapper, который должен быть native-shaped, регистрируется через:

`__registerToStringWrapper(wrapped, nativeFn, wrappedName, wrapperName)`

Модули не создают собственные:

- `Function.prototype.toString` patch;
- WeakMap label registry;
- local nativizer;
- proxy target bridge.

## 13. DEGRADE methodology for Core usage

Core usage events должны соответствовать `3._DEGRADE_Contract.md`.

Обязательный ctx shape:

```js
{
  module,
  diagTag,
  surface,
  key,
  stage,
  message,
  type,
  data
}
```

Допустимые stages:

`bootstrap | preflight | guard | apply | rollback | contract | hook | runtime | cleanup | audit`

Core-specific mapping:

| Situation | stage | expected reason |
|---|---|---|
| target invalid before mutation | `preflight` | `preflight_failed` or concrete Core reason |
| descriptor define/post-check failure | `apply` or `contract` | `apply_failed` / `descriptor_postcheck_mismatch` |
| rollback failure | `rollback` | `rollback_failed` |
| native invalid receiver throws | `runtime` | `native_throw` |
| wrapper bridge registration failed | `apply` | `mark_failed` |
| toString shared state rejected | `preflight` | `realm_baseline_mismatch` / `bridge_target_missing` |

No silent swallow:

- `catch {}` без diag запрещен;
- hook exception может быть converted to native/result pass-through только если diag emitted и contract
  разрешает continuation;
- logging-path failure может быть safe-noop, но patch-path failure не становится success.

---

## 14. Guard methodology for Core users

Связь с `5._GuardFlagSEED.md`:

- guard берется entrypoint-модулем до write side effects;
- `Core.applyTargets` не заменяет guard;
- preflight skip до apply должен снять guard через `releaseGuardFlag(..., true, ...)`;
- fatal after apply требует rollback;
- guard release после fatal разрешен только если rollback clean;
- success path оставляет guard locked.

Нормативный entrypoint flow:

1. Resolve `Core`, `FernwehContext`, logger adapter.
2. Acquire guard через `Core.guardFlag`.
3. Build source/profile/module state.
4. Build target contracts.
5. Call `Core.applyTargets`.
6. Apply Patch Group.
7. Register targets after full success.
8. Keep guard locked on success.
9. On pre-apply skip: diag + release guard.
10. On after-apply failure: rollback + diag + release guard only when rollbackOk.

## 15. Source-of-truth discipline

Core не является хранилищем профильных значений.

Значения должны идти по цепочке:

`profile/dictionaries/bootstrap input -> window.__* / FernwehContext.state.__MODULE__ -> target contract -> Core plan -> descriptor assignment`

Норма:

- Core может проверять structure и descriptor invariants;
- Core может передать `profile` в `applyTargets`, но не должен изобретать значения;
- module обязан доказать источник значения до target creation;
- отсутствующие обязательные данные - diag + skip/throw согласно policy;
- hardcode value внутри Core target без source-of-truth запрещен.

## 16. Разграничение Core / context / module в практике

### 16.1 Standalone module

Standalone module совмещает `module + context`.

Он обязан:

- взять guard;
- построить targets;
- вызвать `Core.applyTargets`;
- применить Patch Group atomically;
- зарегистрировать targets после success;
- выполнить rollback при failure;
- вести DEGRADE diag.

### 16.2 Context module

Context может использовать `Core.preflightTarget`, если descriptor application встроен в hook/issued-object
pipeline и не идет через `Core.applyTargets`.

Но даже тогда context обязан:

- явно задавать `wrapLayer`;
- проверять descriptor owner/shape;
- сохранять descriptor flags;
- делать post-check;
- не создавать local toString bridge.

### 16.3 Domain module

Domain module не должен знать, как устроен toString bridge или wrapper factory internals.

Он должен знать:

- какой external surface он меняет;
- какой `kind` у surface;
- какой `wrapLayer` допустим;
- нужен ли `brand_strict`;
- откуда берется значение;
- какая policy при отсутствии данных.

## 17. Запрещенные применения Core

Запрещено:

- вызывать `Object.defineProperty` на public API без Core preflight, если surface descriptor-sensitive;
- использовать `wrapLayer` missing/auto как норматив;
- переводить весь модуль в `core_wrapper` без per-target receiver/brand основания;
- использовать Proxy carrier только ради красивого `toString`;
- создавать synthetic accessor gateway без native getter вне разрешенного materialized route;
- менять accessor shape на data shape без отдельного внешнего основания;
- регистрировать target до полного group success;
- продолжать после partial apply без rollback;
- проглатывать `Core.applyTargets` exception;
- скрывать native `Illegal invocation` fallback value;
- создавать parallel `Function.prototype.toString` patch;

---

## 18. Минимальный acceptance checklist

Перед применением Core target group нужно проверить:

- external surface classified: data/accessor/method/promise_method;
- descriptor owner доказан через runtime descriptor lookup;
- `wrapLayer` выбран явно;
- `policy` выбран явно;
- `invokeClass` выбран явно, если surface brand/slot/constructor-sensitive;
- `validThis` задан для strict receiver path;
- source-of-truth values существуют;
- no hardcode profile values;
- `Core.applyTargets` доступен;
- registry path доступен или absence observed through diag;
- group apply atomic;
- rollback path exists;
- post-check exists;
- DEGRADE ctx uses allowed stage;
- toString bridge идет только через Core;
- native bad-receiver path не подменен project fallback.

## 19. Открытые риски текущей реализации

Эти пункты не являются требованием немедленно менять код. Они фиксируют места, где применение Core
должно быть особенно осторожным.

1. В `patchDataProp` текущего Core есть compatibility branch, допускающий `wrapperClass` на data path.
   По нормативной модели `kind=data` должен оставаться `descriptor_only` / `descriptor_data`.
   Использовать эту ветку как новую норму нельзя.

2. Некоторые caller-модули применяют `nextDesc` вручную через `Object.defineProperty`, а не через
   `planItem.apply()`. Это допустимо только при сохранении того же post-check/rollback/registry
   discipline. Предпочтительный прикладной path - `p.apply()` / `p.rollback()`.

3. `diagDegrade` fail-safe проглатывает сбой logging-path. Это разрешено `DEGRADE`-контрактом только
   для logger failure. Любая patch/preflight/apply ошибка должна оставаться observed или fail-fast
   согласно policy.

4. Полное соответствие всех текущих target lists этому документу не доказано этим документом.
   Для доказательства нужен отдельный аудит всех вызовов `Core.applyTargets` и `Core.preflightTarget`.

## 20. Контрольные критерии валидности применения `Core`:

1. Module определяет внешний surface contract.
2. Module берет source-of-truth values из profile/state/window sources.
3. Module/context строит explicit target contract.
4. `Core` делает read-only preflight и batch planning.
5. `Core` выбирает один из четырех dispatch paths: data/accessor/method/promise_method.
6. `Core` wrapper/toString bridge используется только через единые factories/registration.
7. Caller применяет Patch Group atomically.
8. Caller регистрирует targets только после полного success.
9. Failure path всегда идет через diag + rollback/throw по policy.
10. Внешний ECMAScript/Web IDL контракт всегда главнее internal Core labels.
